Section 1

The Architecture: MOTHER Plus Five Executives

The old estate had functions such as ROUTER, BuildOps, RepoRescue, KeyGuard, LaunchOps, ContentOps, IPLibrarian, SalesOps, ClientOps, DataOps, FinOps, ResearchOps, QAGate, RepoHygiene, Governance, Session Scribe, MOTHER, FATHER, AXIOM, and Builders. Directionally correct, structurally too fragmented for modern high-context Grok agents. Those become skill modules. Five Grok personalities get durable context and authority. MOTHER decides which personality receives the task and which skills it loads. Click any agent to read its role.

The example the conversation gives. "Figure out why DeedSonar production differs from Cursor." MOTHER does not create an eight-agent committee. It routes: primary FORENSIC, with skills RepoRescue, DataOps, QAGate, RepoHygiene, and Governance, and AXIOM in support. The filing marks the support line as truncated in the browser view; the full line is not available, and this page does not complete it.

The crucial rule. MOTHER does not do specialist work simply because it can. It routes. Otherwise the hub gradually becomes another giant chatbot and the architecture collapses back into a single-agent mess.

Section 3

The Dual-Core Protocol

Every consequential agent operation follows the same sequence. Shadow mode cannot merely summarize the primary answer. Its job is to falsify it. For high-consequence work, an independent review goes to another executive agent so both primary and shadow are checked. Click any stage to read what it does.

MOTHER-WATCH observes: health, heartbeats, session ingestion, Git and repo drift, stale work, failed jobs, permissions, cost anomalies, unfinished handoffs, artifact custody, dead-letter queue, receipt completeness, canon conflicts. It does not hallucinate completion. MOTHER-ACT orchestrates: interpret the objective, resolve canonical context, classify risk, build the dependency graph, choose the agent, load skill modules, issue the MCP task envelope, watch progress, route failure, request shadow review, run the verification court, record the receipt, promote verified state.

FORENSIC exists because AXIOM should not be permitted to explain away its own failures. It does not build features while an incident is open. It determines what exists, what changed, where, when, by whom, which version, which state is authoritative, what is missing, what is recoverable, and what is live. Its evidence vocabulary is mandatory: PROVEN, PROBABLE, CONFLICTED, UNKNOWN, FALSE. Not "probably done," "looks live," "should be merged," or "seems fixed." Only after root cause is proven does the SURGEON operate: break it, locate root cause, fix it, retest, connect missed seams, verify runtime, produce the receipt.

Section 4

Typed Truth Authority

The older documentation had a real inconsistency: one doctrine describes Obsidian to GitHub to Notion, while other material treats Supabase and Notion as the operational truth layer. The V3 answer is not to force one source to be authoritative for every asset type. It is typed authority. This one decision, the conversation argues, removes a large amount of future gaslighting-by-state-drift.

InformationAuthority
Proprietary concepts, specifications, frameworksNEURUH IP VAULT
Executable source codeGitHub branch + SHA
Live runtime and database factsRuntime + Supabase / database query
DeploymentProvider / runtime receipt
Operational routing and statusNotion Command / Run Ledger
Resale and asset logicFindSellProfit / ResellOS canon
Previous session statementsEvidence only until reconciled
Current laws, docs, marketsCurrent first-party web sources
Model memoryLowest authority

Source resolution algorithm. For every factual claim: classify the claim type, select the correct authority, retrieve the source, capture the timestamp or version. Indexed lookup runs approximately O(s log n) for s sources and n indexed records. A naive full scan runs O(s n). Conflict reconciliation over r retrieved candidates runs O(r log r). Provenance DAG traversal runs O(V + E).

Task planning complexity. Routing across k executive agents is O(k), effectively constant-time with five agents. Dependency planning by topological scheduling is O(V + E). Parallel execution costs O(sum of Ti) in total compute and O(max Ti) wall-clock under perfect parallelization. Shadow review is asymptotically O(T) but intentionally adds approximately another reasoning pass. That extra compute is not waste. It is insurance against bullshit.

Idempotency. Every job gets a task id, idempotency key, lease owner, lease started, lease expires, attempt, parent, status, and last heartbeat. Before mutation: check receipt, check existing lease, check target hash, acquire lease, mutate, verify, receipt. Indexed lease lookup is O(log n). Append-only receipt is O(1) amortized. The overlap guard comes from the old Poised Guardian doctrine: stacked schedules could fire concurrently, so every scheduled job checks for an existing active run before starting, and if one is already active it does not start a duplicate.

Activation cadence. Do not make all five agents blindly wake every ten minutes. That was useful when the agents were primitive. MOTHER runs continuous and event-driven plus heartbeat. Poised Guardian is event-driven plus a scheduled operational sweep. AXIOM fires on code, build, and repo events. Da Vinci fires on design and frontend requests. CAPITAL fires on new signals plus a scheduled opportunity sweep. FORENSIC fires on failure, conflict, stale state, and release audit. Shadow cores fire on every consequential output. Builder 2.0's historical logs show why the old pattern became noisy: repeated cycles often produced heartbeat-only output with no new work.

Section 6

Risk Lanes: GREEN, YELLOW, RED

The older Guardian doctrine already used almost exactly this distinction. GREEN is autonomous. YELLOW requires approval. RED requires explicit principal authority, and some RED actions no autonomous agent should independently take at all.

LaneWhat it covers
GREEN: autonomousSearch internal data, classify, score, draft, test, create local branches, create receipts, update operational logs, run non-destructive analysis, perform QA.
YELLOW: approval requiredSending external email, contacting prospects, publishing, production deployment, CRM outreach, charging or refunding, contracting, personalized financial offers, acting on consumer data, potentially regulated real-estate communications.
RED: explicit principal authoritySigning contracts, executing securities transactions, committing lending decisions, making regulated investment recommendations as an adviser, altering IAM, rotating credentials without authority, exposing secrets, deleting canonical data, bypassing consent and DNC requirements, materially representing guaranteed investment or business earnings.

Failover. No agent's private chat history is authoritative. Task state, decisions, artifacts, hashes, receipts, handoffs, leases, errors, and rollback pointers persist outside the model. If MOTHER is unavailable, Poised Guardian enters COMMAND-GAP mode, freezes risky autonomous writes, and routes critical work. The filing marks the rest of that line as truncated in the browser view. If Poised Guardian is unavailable, AXIOM becomes Acting Chief of Staff for operational and build work only, with no policy mutation. If AXIOM is unavailable, FORENSIC recovers engineering state but may not expand features. If CAPITAL is unavailable, revenue opportunities queue, and no other agent improvises financial strategy. If Da Vinci is unavailable, AXIOM may ship functional UI but may not redefine the design canon. Every material artifact has at least a Git commit and SHA, a durable storage copy, a receipt, and a canonical index pointer.

Write control. Single-writer leases. Before mutation: check existing receipt, check lease, check target version and hash, acquire lease, mutate, verify, write receipt, release. No two agents may write to the same artifact simultaneously. The old Custom Agent page rule is kept: agents mutate operational state only through proposed patches, not by casually overwriting narrative canon, with a weighted scorecard and acceptance before promotion.

Section 7

Certification: Ten Tests Before Autonomy

No Grok agent enters autonomy because its prompt sounds smart. Each must survive ten tests. Click any test for what it demands and what the correct outcome is.

Startup court. If the agent cannot populate its status block truthfully, it must not mutate. Rule: no mutation without a truthful status block. Succession files. The agent canon should become a real Git-backed repository, not live only inside Grok configuration screens. Every agent must contain SYSTEM.md, PRIMARY.md, SHADOW.md, SKILLS.yaml, AUTHORITY.yaml, TESTS.md, and CHANGELOG.md. MOTHER must additionally contain ROUTING.yaml, FAILOVER.md, MCP schemas, receipt schemas, and risk policies. No production prompt may exist only inside Grok UI. Every deployed prompt must include an agent id, a semantic version, a source commit SHA, a build date, and a source manifest hash.
