1. Why this run is different

Most multi-agent demos are a prompt and a hope. LEGION is a lease, a supervisor, a journal, and a seal. Six properties set the 2026-09-28 run apart, and each one is enforced in code, not requested in prose.

  • Builder separate from judge. The code that scores a lead never certifies its own work. Scoring and certification are different components with different authority, and the seal comes from the roll-up, not from the scorer's self-report.
  • Crash resume to byte-identical output. A run killed mid-flight resumes from the hash-chained journal and produces the same FINAL_OUTPUT hash. The resume is a property of the journal, not a fresh run that happens to agree.
  • Sealed roll-up. Squad seals roll into cohort seals, and cohort seals roll into one FINAL_OUTPUT seal. Tamper with any layer and the seal above it fails.
  • HALT kill switch. A HALT flag stops the run before the next unit of work starts. The supervisor checks it; agents do not get a vote.
  • Tampered journal halts the run. The hash chain is verified on resume. A broken link stops everything instead of papering over the gap and continuing on edited history.
  • Limits enforced in code, not prompts. Fixed thread pool, read-only agents, and a 25,000-agent hard limit. The ceiling is a constant in the runtime, not an instruction an agent can talk its way past.

2. The honest scorecard

What ran on 2026-09-28 was 6,487 deterministic scoring units in parallel, each leaving a receipt, under one supervisor with a kill switch, sealed into a single output. No large language model ran in the main loop. No agent negotiated with another agent. Nothing on this page is a mind, and nothing here is learning.

Say it plainly: 10,000 scorers running in parallel is parallel processing with receipts, not swarm intelligence. The honest name for this run is governed parallel scoring with a sealed roll-up. That is still a real achievement, because the hard part was never the parallelism. The hard part was the governance: identity before scoring, a journal that cannot be quietly edited, a resume that reproduces the same hash, and a seal that fails loudly when anything underneath it changes.

3. The stack

  • neuruh-workers runtime. The lease host. LEGION runs as a governed lease inside the workers runtime, not as a standalone process. The runtime owns the thread pool, the supervisor lock, and the HALT path.
  • Chapter 04 chain of custody. Every input carries identity and provenance before scoring starts. A lead with no provenance does not enter the run.
  • Switchboard. Routes scored work to the fixed thread pool and back to the roll-up.
  • Sentinel. Governance and the HALT path. The supervisor answers to Sentinel; the agents answer to the supervisor.
  • Heartwood Arborist, second job type. The same lease shape running a different job: scan a codebase and score it. Recorded 2026-10-05: 12 commits, 326 of 326 tests passing. Recorded, not re-verified from here.
  • funding_fit, third job type, in progress. A third job type on the same lease shape. Status unknown; recorded as in progress, not verified.

4. Mechanics, step by step

  1. Input identity. Every lead enters with identity and provenance under the Chapter 04 chain of custody.
  2. Supervisor lock. One supervisor owns the run. A second run cannot start on the same lease while the lock is held.
  3. HALT check. Before each unit of work, the supervisor checks the HALT flag. A set flag stops the run before the next agent starts.
  4. Resume hash-chain verify. On restart, the journal hash chain is verified before any agent runs. A broken chain halts the run.
  5. Fixed thread pool. Concurrency is bounded in code. Agents do not spawn agents.
  6. Read-only agents. Agents score. They do not write, call out, or change state. All writes go through the supervisor into the journal.
  7. Hash-chained journal. Every agent action appends a hash-chained journal record. The journal is the run's memory and its evidence.
  8. Squad sealing. Each squad of 50 (last squad 37) seals its roll-up.
  9. Cohort sealing. Squad seals roll into 7 cohort seals.
  10. FINAL_OUTPUT sealing. Cohort seals roll into one sealed FINAL_OUTPUT.
  11. Ledger records. 11 ledger records per run. Recorded 2026-09-28.

5. D-046: open rulings

Two decisions are open, and both are Jeramie's calls. Nothing in the path to a public surface moves until they are ruled.

Packaging: how does the Heartwood dependency ship?

  • Option A: deploy key. The runtime pulls the private Heartwood repo with a deploy key.
  • Option B: make Heartwood public. The repo becomes public and the dependency is ordinary.
  • Option C: copy the package. The needed package is copied into workers, and the dependency goes away.

Status: unruled. Recorded 2026-10-05.

Judge inside the builder: who certifies workers?

Workers depends on Heartwood, and Heartwood scans workers. A certification produced by the in-runtime scanner would be the builder judging itself. The ruling on the table: workers is certified only by the standalone CLI, never by the in-runtime scanner. Status: unruled. Recorded 2026-10-05.

6. The path to a live surface

Planned, not built. LEGION-LIVE is the operator surface that would turn the replay into a watched run. The plan, as recorded:

  • LEGION-LIVE :8620, operator surface. Full detail for the operator: squads, cohorts, journal tail, HALT control.
  • LEGION-LIVE :8621, aggregate-only surface. Counts and seals only. No lead fields, enforced by a server-side field allowlist, plus a negative test that fails if any lead field leaks.
  • --events journal tail, default OFF. An opt-in journal tail with a hash-identity proof: the same FINAL_OUTPUT hash with the option on and off.
  • Paced runs. The NC re-run and the 10,000-agent fault-injection run, deliberately slowed so a human can watch the structure form. Labeled on the surface as "PACED: real run, deliberately slowed".
  • launchd. com.neuruh.surface.legion-live keeps the surface up on the Mac.

Two questions stay open for Jeramie. Who can see it: local-only, a public aggregate link, or legion.neuruh.com behind Cloudflare Access? And what does it run: the NC re-run, a Heartwood Arborist scan, or both? Both needs the D-046 rulings first.
