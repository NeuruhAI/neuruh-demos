Retardio Measurement Loop v1

The first working piece of Retardio — the system name when complete. Narrow first: one county, one public source, three forecast types, one scoring rule. Everything else (authority headers, topology, weight updates) waits until this loop produces calibrated forecasts on held-out data.

Strengthen, do not remove: this is additive. It replaces nothing in the estate. Note: the name Retardio is also used by a Solana memecoin; this system is unrelated.

1. The narrow loop

Chosen domain. Public county property records + related entity filings, focused on patterns that appear in published fraud, money-laundering, and scam typology reports: all-cash LLC purchases, rapid flips with large unexplained jumps, newly formed entities with no clear activity, clusters of properties controlled by related entities. This is fully public in most U.S. counties. Outcomes can later be coded from court dockets, news, enforcement actions, or subsequent public filings. It stays at the level of transactions and entities, not private individuals scored as corrupt.

County. St. Joseph County, Indiana. One source to start: the county assessor's public ArcGIS parcel service. No other data source is added until this loop produces calibrated forecasts on held-out historical data.

  1. Ingest observations from one county into the append-only log.
  2. On each new relevant observation, emit the applicable forecasts with receipts.
  3. Wait for natural resolution windows or public outcomes.
  4. Code outcomes and compute Brier.
  5. Only after a stable Brier is demonstrated on historical back-test + forward test, allow a human-reviewed proposal to adjust the scoring rule.
  6. Re-test the adjusted rule on new data. Keep it only if Brier improves.
  7. All steps produce receipts. An independent party can re-compute hashes and Brier from the exported log.

2. Layer 1 — Observation schema

Every observation is a structured record with provenance. Nothing enters the system without a hash. Canonicalize before hashing: sorted keys, normalized strings (first line of names, whitespace collapsed), numbers as integers when whole. Store the raw bytes so the hash can be recomputed by an independent party. Append-only log: no updates; corrections are new observations that reference the prior ID. Retrieval method and parameters are in the source locator so the observation can be reproduced.

{
  "observation_id": "sha256 of canonical payload",
  "source": "county_recorder | secretary_of_state | court_docket",
  "source_locator": "county + instrument_number or filing_id + retrieval_timestamp",
  "retrieved_at": "ISO-8601",
  "raw_hash": "sha256 of exact bytes retrieved",
  "entity_type": "deed | llc_filing | ucc | lis_pendens | judgment",
  "payload": {
    "instrument_date": "...",
    "grantor": "...",
    "grantee": "...",
    "consideration": "number_or_null",
    "property_id": "parcel or address hash",
    "entity_name": "...",
    "formation_date": "...",
    "related_entities": ["..."]
  },
  "schema_version": "1.0"
}
Source vocabulary, one honest extension. The available first source is the county assessor's ArcGIS parcel service, not the recorder, so the log uses county_assessor_arcgis and parcel_record where the spec's enum does not cover them. The assessor carries the sale fields a deed carries (sale date, consideration, grantee), but it is not the recorder: it shows only the latest sale per parcel, it carries the current owner rather than the grantor, and it carries no entity formation dates. Deed-history resolution still needs the recorder. Fields the source does not carry are null, never invented: grantor, formation_date, related_entities. acreage is carried as a documented payload extension because the scoring rule uses it. Street addresses are not published on this page; property_id is the county parcel ID. raw_hash is the SHA-256 of the canonical form of the retrieved feature record (sorted keys; whole-number floats rendered as integers; strings as returned); the response file is preserved so anyone can recompute it from the same rule.

Click any observation row (or press Enter while it is focused) to expand the full record: observation_id, raw_hash, source, source_locator, retrieved_at, and the full payload. Click again to collapse.

Corrections to date: 0. The log is append-only; a correction would appear here as a new observation referencing the prior ID.

3. Layer 2 — Forecasts (pre-registered, receipted)

Three forecast types, defined in the spec. Each forecast is emitted before its outcome is known and stored with its own receipt. Two of the three cannot be issued yet, and the page says why instead of faking them.

baseline_v1 — the transparent scoring rule

The initial model is a transparent rule on the features, not a fitted model. Coefficients are stated assumptions, not measured rates. The point is that every probability is issued in advance and later scored.

baseline_v1 (rapid_flip):
  prior                                0.04
  +0.03 if consideration < $100,000
  +0.02 if acreage < 0.5
  clamp to [0.01, 0.50]
  features_used: ["consideration", "acreage"]

Assessed value is deliberately not a feature: current-snapshot assessed values would be look-ahead for a back-test as of the sale date. Sale price, sale date, and acreage are fixed at the deed. Class code is not used: the Indiana class-code mapping was not verified for this build.

Back-test, not live issuance. These forecasts were computed at build time from the rule above, applied retrospectively to historical deeds, with issued_at set to each sale date. The rule was fixed on 2026-11-15 before any outcome was coded. That is what makes this a valid back-test design: the rule is frozen before outcomes are known. A live forecast (issued at observation time, window still open) will appear here only when a deed feed exists. No outcome has been coded for any of these forecasts.

4. Outcomes + Brier

When a window closes or a public record resolves the question, an outcome record is written:

{
  "outcome_id": "...",
  "forecast_id": "...",
  "resolved_at": "...",
  "outcome": "0 or 1",
  "evidence_observation_ids": ["..."],
  "coder": "human | rule",
  "receipt": "..."
}

Brier score, for a set of resolved forecasts: Brier = (1/N) Σ(pi − oi)². Lower is better. Tracked overall, by forecast type, and over time. Published here. A model or weight update is retained only if it improves Brier on a subsequent or held-out set, not the set used to propose the change.

5. Promotion gate

A change in scoring or topology is retained only if it improves a pre-specified metric (Brier) on data not used to propose the change. This is recursive only in the narrow sense of improving the measurement apparatus. It is not recursive self-modification of arbitrary code.

Status: no proposal pending. No scoring change can be proposed until a stable Brier exists on the back-test set, and no change can be retained until it beats that Brier on a held-out set. The gate is armed, not triggered.
