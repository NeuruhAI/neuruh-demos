A working in-browser demo of the Master Command Protocol (MCP) as the sources state it: a central hub that routes, holds state, and decides, with specialized spokes that each do one function. Static HTML and JS only. No backend. Nothing leaves this page.

The six spokes below are the six systems AI-FW-018 lists under "Applied across". Their single-function labels are builder labels (mine), derived from the system names only.

No line connects any two spokes. Every path runs through the hub. That is rule R1, drawn literally.

RuleSourced text (short form)What the simulator enforces
R1No spoke communicates with another spoke directly. All routing through hub.Section 4: a DIRECT attempt is BLOCKED and rerouted through the hub.
R2Each spoke is stateless. Hub holds all session state.Section 3: task records live in hub session state. Spokes hold none. Failover resumes from hub state.
R3Failover: if a spoke fails, hub reroutes to backup spoke in under 200ms.Section 5: failover to a standby twin, simulated elapsed time inside the budget.
R4Role-switching: hub dynamically assigns spoke roles based on task queue and capacity.Section 6: role assignment from queue depth and capacity.

3. Command parser: talk to the hub

The command grammar is a builder design decision (mine). The sources state the hub is the central router and decision authority but give no command syntax. The parser shows every step: tokenize, verb, arity, authority class, dispatch.

Verbs: ROUTE <spoke> <task>, STATUS [HUB | <spoke>], FAILOVER <spoke>, ASSIGN <spoke> <role>, RETRY <task-id>, DIRECT <spoke-a> <spoke-b> <message>. Spoke ids: dispatch-iq, vla-arbitrage, baker-hvac, pulsar-dc, geointel, roof-ops.

No command run yet this session.

Authority classes are builder design (mine): STATUS and ROUTE are AUTO, FAILOVER and ASSIGN are HUB-DECISION, RETRY is GUARD under the Permission Guard name from L2 with the retry cap from AI-FW-002, DIRECT is BLOCKED by R1. No authority or gating mechanics are stated for MCP in the sources.

5. Failover simulator: R3

Mark a spoke failed. The hub reroutes to a standby twin. The source states rerouting completes in under 200ms but names no backups, so the standby twin is a builder design (mine) and the elapsed time is simulated, computed from queue depth, and labeled simulated.

No failover yet this session. A failed spoke refuses new routes until failover runs; try routing to it first.

6. Role-switching simulator: R4

The hub assigns a spoke role from task queue depth and capacity. The source states the hub assigns roles based on task queue and capacity but gives no rule, so the decision rule is a builder design (mine): load above 1 is OVERLOAD, at or above 0.5 is BUSY, below 0.5 is IDLE.
