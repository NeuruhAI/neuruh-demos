Sovereign Compounding Runtime

The inbox-to-capsule daemon the paste sketched, finished to production as a single-node system. Raw dumps go in, capsules come out: atomized, linked, cascade-propagated, invariant-gated, receipted in a hash-chained SQLite ledger, published to a durable NATS JetStream stream, decided through signed founder tokens, and verified by webhook and database runners. The paste claimed all of it and proved none of it. This runtime proves it.

02What was built

  • sovereign_runtime/codex.py: the 13 invariants, 5 state levels, lifecycle order, authority allowlist, resource caps, link threshold 0.15, cascade decay 0.6, depth 3, floor 0.05, signal score weights.
  • sovereign_runtime/models.py: Pydantic models for Capsule, Link, CascadeTouch, Receipt, FounderGate, and InvariantVerdict. Capsule state must be one of the five levels; lifecycle must be DRAFT, ACTIVE, SUPERSEDED, or RETIRED.
  • sovereign_runtime/invariants.py: all 13 invariants mapped to enforceable checks. Halts stop ingestion with a rejection receipt. Gates open a founder gate and hold the capsule. Never a fake pass.
  • sovereign_runtime/store.py: SQLite persistence: capsules, links, an append-only event log, founder gates, meta, durable workflows, notifications, verifications, and audit flags. Hash-chained receipts using the same canonical JSON scheme as the ontology runtime, so the two ledgers share one receipt format. Chain verification recomputes every hash.
  • sovereign_runtime/engine.py: the compounding engine: atomize, invariant gate, computed signal score, Jaccard linking, decay cascade, founder gate decide and ingest-held, archive through an approved gate, rescoring. Gate decisions require a verified founder capability token; the name-string path is removed.
  • sovereign_runtime/watcher.py: inbox watcher with a configurable workspace path. Ingested files move to archive. Files that open a founder gate move to held. Files that halt move to rejected. A held or rejected file never re-triggers on the next poll.
  • sovereign_runtime/auth.py: HMAC signed capability tokens. Secret from SOVEREIGN_TOKEN_SECRET, never in the repo. Roles founder, operator, reader with scoped permissions. Forged, tampered, and expired tokens are rejected.
  • sovereign_runtime/bus.py: NATS JetStream event bus. Stream SOVEREIGN_RECEIPTS, subjects sovereign.receipts.> and sovereign.outcomes.>. The server publishes every new receipt; a durable subscriber reads them back. A high-water mark in meta keeps restarts from republishing the ledger.
  • sovereign_runtime/server.py: FastAPI server, the single owner of the store. Endpoints for health, status, ingest, capsules, receipts, gates, gate decisions, workflows, notifications, verifications, Stripe and generic webhooks, database row verification, and the auditor. Every endpoint except health requires a bearer capability token.
  • sovereign_runtime/mcp_gateway.py: MCP gateway, JSON-RPC 2.0 over stdio. Tools: ingest, gates_list, gate_decide, status, receipts_list, verify_chain, workflows_list. Gate decisions require a signed founder token.
  • sovereign_runtime/workflows.py: durable workflow runner. Long-running work suspends on a founder gate in SQLite and resumes across process restarts. States RUNNING, SUSPENDED, RESUMED, COMPLETED, DENIED.
  • sovereign_runtime/notify.py: notification bus. Exactly one dispatch per gate, enforced by a UNIQUE gate_id constraint. File outbox is the proven default; a Resend sender is wired behind RESEND_API_KEY and SOVEREIGN_NOTIFY_EMAIL and refuses to construct until both are set.
  • sovereign_runtime/webhooks.py: verification runners. Stripe webhook signature verification (HMAC v1 scheme) promoting the capsule in the event metadata from observed to verified, a generic HMAC webhook, and a database row check runner that promotes a capsule when a real SQLite row exists.
  • sovereign_runtime/audit.py: background auditor. Re-validates the hash chain and flags tampered receipts, orphan capsules, orphan links, and deleted receipts. Checkpoints after each clean sweep so the next sweep can detect deletion.
  • sovereign_runtime/backup.py: online SQLite backup, rotation (keep 7 by default), SHA-256 manifest, chain verification on the backup copy.
  • sovereign_runtime/cli.py: python -m sovereign_runtime init | ingest | watch | status | gates | verify | token | serve | mcp | audit | backup. Gate decisions take --token; the old --by name flag is gone.
  • tests/: 117 tests covering term extraction, Jaccard math, signal score formula, cascade decay to the fourth decimal, all 13 invariants, gate approve and deny, receipt chain validity and tampering, restart persistence, watcher behavior, token forgery, tampering and expiry, NATS publish/subscribe and restart persistence, server auth and gate flows, workflow suspend and resume across restarts, exactly-once notification dispatch, Stripe signature verification and promotion, database row checks, auditor tamper detection, backup rotation and verification, and the MCP gateway over stdio.
  • scripts/run_e2e_v2.py: the production end-to-end execution that produced the receipt below, including the NATS restart proof and the server restart/resume proof.
  • deploy/: Dockerfile, docker-compose.yml (server plus NATS), systemd units for Linux, and a Mac launchd plist.

03The thirteen invariants, as enforced

Every invariant maps to a check the engine runs on every ingestion, in order. HALT stops ingestion and writes a rejection receipt. GATE opens a founder gate and holds the capsule until a founder decides.

IDInvariantEnforceable checkOn failure
INV-01Identity is singularOne canonical id, one capsule. A second capsule claiming an id that exists with different content halts. Identical content under the same id halts as a duplicate.HALT
INV-02State is explicitThe capsule must declare one of the five state levels. No state means no ingestion.HALT
INV-03Evidence is traceableAt least one evidence ref, and a non-empty source ref. No source means no ingestion.HALT
INV-04Authority is boundedThe writer must be a known authority: sovereign-runtime, jeramie-hicks, or founder. Anything else halts.HALT
INV-05Resources are finiteRaw content capped at 50,000 bytes, terms capped at 400. Over either cap halts.HALT
INV-06Context changes weightA signal score is only valid against the corpus version it was computed from. A stale score halts until rescored.HALT
INV-07Learning is governedLinks and cascade updates are only written by the engine through receipts. A draft without an engine receipt marker halts, and a link write without a receipt id is refused.HALT
INV-08Irreversibility needs stronger evidenceArchive and delete are never executed automatically. They open a founder gate.GATE
INV-09Every object has a lifecycleLifecycle must be DRAFT, ACTIVE, SUPERSEDED, or RETIRED, and transitions only move forward. A backward move halts.HALT
INV-10No core forksIdentical content under a different id is duplicate truth. The founder picks the canonical id.GATE
INV-11Outcomes outrank narrativesAn outcome claim must cite an observed receipt id in its evidence. A narrative claim with no receipt opens a founder gate.GATE
INV-12Negative evidence stays visibleA capsule update may not drop a conflict unless it records the superseding receipt. Dropping one silently halts.HALT
INV-13Complexity must pay rentTerms over 400 or links over 10 must be split. Over either cap halts.HALT

04Signal score, computed

The paste hardcoded 90.0 on every capsule. The score here is computed from the live corpus at ingestion time:

novelty = 1 - max Jaccard similarity to any existing capsule
          (1.0 when the corpus is empty)
link_density = min(1, number of links / 5)
signal_score = round(100 * (0.6 * novelty + 0.4 * link_density), 2)

Worked numbers from the v2 run: the first capsule ingested, cap-repurpose-engine, scores 60.0 (novelty 1.0, no links yet). The most connected capsule, cap-card-id-system with 5 links, scores 72.44. A capsule identical to one already stored scores 0 on novelty and halts on INV-01 before a score is ever written. Scores are stamped with the corpus version they were computed against; INV-06 halts a stale score until it is rescored.

05The decay cascade, for real

When a new capsule links to an existing capsule at hop 1 with strength s, the update propagates to that capsule's neighbors at hop 2 with strength s * 0.6, and to their neighbors at hop 3 with strength s * 0.36. Propagation stops at depth 3 and below strength 0.05. A capsule reachable by several paths keeps the strongest value. The source capsule is never a cascade target. Every touch is recorded on the capsule and in its own receipt.

End-to-end numbers: 28 cascade touches, max hop 3, total propagated strength 5.8398. The cascade reached hop 3 because the graph has a sparse edge: the advertising index links only to the design index, so updates flow design to advertising to the rest of the graph through the decay.

07The production proofs

  • Event bus. NATS JetStream v2.15.3, stream SOVEREIGN_RECEIPTS. The server published every receipt; a durable subscriber read 52 of them back. Then 3 marker messages were published, NATS was stopped and restarted, and the subscriber read all 3 markers after the restart. Kafka is not runnable on this VM (JVM plus KRaft, far more memory than this cell has); the page states the choice plainly.
  • Server restart and resume. The gate opened through the API, the workflow suspended in SQLite, and the server was killed and restarted with the gate open. The gate was still PENDING and the workflow still SUSPENDED after the restart. An operator token approval was refused with 403. A founder token approval resumed the workflow and the held capsule was ingested.
  • Notifications. Exactly one dispatch for gate gate-606328b2: one file in the outbox, one notification record, one GATE_NOTIFICATION_SENT receipt. The notification carries the gate id, capsule id, invariant, and the approve/deny curl commands with a token placeholder, never a real token.
  • Verification runners. A locally signed Stripe test event (evt_e2e_v2_1) promoted cap-validation-loop from observed to verified. A bad signature was rejected with 401 and no state change. A database row check promoted cap-repurpose-engine to verified. The real Stripe webhook secret is Jeramie's to supply.
  • Tamper detection. On a copy of the store, a direct receipt edit and a direct capsule insert were both flagged by the auditor (TAMPER_CHAIN and ORPHAN_CAPSULE) and the copy chain verified as invalid. The live store audits clean. Plain statement: on a single machine a shell user with file access can still write the database. The mitigation is permissions plus detection, not prevention.
  • Backup. An online backup was taken during the run and its hash chain verified. SHA-256 b17f1b4b2a503d63...
  • MCP gateway. JSON-RPC 2.0 over stdio answered status (9 capsules), verify_chain (valid), and gates_list (1 gate, APPROVED).

09Mac run-book

On the M1 Mac, the workspace is ~/neuruh-workspace. Exact commands:

cd ~/workspace/sovereign-runtime
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m pytest tests/ -q
.venv/bin/python scripts/run_e2e_v2.py

NATS, one time (downloads the darwin arm64 binary from GitHub):

sh scripts/install_nats.sh
mkdir -p ~/neuruh-workspace/nats
./bin/nats-server -js -sd ~/neuruh-workspace/nats -p 4222 -m 8222

Token secret, one time. Keep it out of the repo, out of chat, out of receipts:

export SOVEREIGN_TOKEN_SECRET="$(python3 -c 'import secrets; print(secrets.token_hex(32))')"

Save that value in ~/.sovereign-runtime-env. Mint tokens:

.venv/bin/python -m sovereign_runtime --workspace ~/neuruh-workspace token --role founder --subject "Jeramie Hicks"
.venv/bin/python -m sovereign_runtime --workspace ~/neuruh-workspace token --role operator --subject "operator"

Start the server:

SOVEREIGN_WORKSPACE=~/neuruh-workspace SOVEREIGN_TOKEN_SECRET="$SOVEREIGN_TOKEN_SECRET" SOVEREIGN_NATS_URL=nats://127.0.0.1:4222 .venv/bin/python -m sovereign_runtime --workspace ~/neuruh-workspace serve --host 127.0.0.1 --port 8765

Or install the launchd plist for start-on-login (replace USERNAME in deploy/com.neuruh.sovereign-runtime.plist first):

cp deploy/com.neuruh.sovereign-runtime.plist ~/Library/LaunchAgents/
launchctl load ~/Library/LaunchAgents/com.neuruh.sovereign-runtime.plist

Approve a gate through the API (same token, resume on reply):

export FOUNDER_TOKEN="$(.venv/bin/python -m sovereign_runtime --workspace ~/neuruh-workspace token --role founder --subject "Jeramie Hicks")"
curl -s -X POST http://127.0.0.1:8765/gates/gate-XXXX/decide -H "Authorization: Bearer $FOUNDER_TOKEN" -H "Content-Type: application/json" -d '{"approve": true}'

Health, audit, and backup:

curl -s http://127.0.0.1:8765/health
.venv/bin/python -m sovereign_runtime --workspace ~/neuruh-workspace audit
.venv/bin/python scripts/backup.py --workspace ~/neuruh-workspace --keep 7

Drop any raw text file into ~/neuruh-workspace/inbox/. Processed files move to ~/neuruh-workspace/store/archive/. Files that open a founder gate move to ~/neuruh-workspace/store/held/. Files that halt move to ~/neuruh-workspace/store/rejected/. Gate notifications land in ~/neuruh-workspace/store/outbox/. Receipts live in ~/neuruh-workspace/store/capsules.db.

File convention: a line starting with OUTCOME: means the dump claims an outcome. Without an observed receipt in evidence, INV-11 holds it for a founder decision. List pending gates with gates, approve one with gates --decide gate-XXXX --approve --token "$FOUNDER_TOKEN", then re-ingest the held file.

10What is still missing

  • Distribution: one node, one SQLite file. No Kafka, no Postgres event store, no multi-agent streaming. NATS JetStream is the durable broker for this node.
  • Orchestration: no Temporal. The durable SQLite workflow runner resumes across restarts on one machine; it is not a distributed scheduler.
  • Notifications: Resend email is wired but unconfigured until Jeramie supplies RESEND_API_KEY and SOVEREIGN_NOTIFY_EMAIL. The file outbox is the proven path today.
  • Verification: the Stripe runner is proven with a locally signed test event. The real webhook secret is his to supply, and Stripe events must carry metadata.capsule_id.
  • Middleware: the auditor detects out-of-band writes; it cannot prevent a shell user with file access from making them. Permissions plus detection, not prevention.
  • Deployment: no hosted deployment ships from here. Docker, systemd, and launchd packages are in deploy/; the target is his Oracle VM or his Mac.
