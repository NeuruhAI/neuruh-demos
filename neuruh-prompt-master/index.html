1. Scope and grounding method

This document is the master record for Neuruh prompt systems as of 2026-11-18. It covers four things: the Prompt Builders app and its 26 builders, the Examples Library that sits inside it, the named prompt patterns (PMLA, SAL, Token-Swap, and the general brief builders), and the Neuruh Prompter tool. It also records the two brief items that could not be grounded, so they are not silently dropped and not silently invented.

Grounding method. Every count in this document was computed from the live source files on 2026-11-18, not copied from memory. Builder counts, field counts, template character counts, states, and example counts were computed directly from builder-spec.json (spec v1.1, generated 2026-11-18) and cross-checked against examples-seed-inventory.json (generated 2026-11-18) and the live Prompt Builders page header, which reads: 26 builders, 298 fields, 16 live, 10 designed, 2 need your call, 125 examples (115 prompts, 10 outputs). All three sources agree. Pattern entries were checked against the Retardio Library seed index (1,103 records, audit date 2026-11-18), the Drive inventory, and the segment program docs. The Neuruh Prompter entry was checked against the segment Tools and Utilities inventory, report, marketing, and demos docs.

State ladder used throughout: CONCEPT, DESIGNED, IMPLEMENTED, TESTED, DEPLOYED, LIVE, PROVEN, COMMERCIAL, BLOCKED, UNKNOWN. A state is only claimed when a source states it or the evidence supports it. Where a source is silent, the entry is UNKNOWN with the reason.

What this document does not do: it does not reproduce prompt text. Template presence is reported as a verified character count from template_verbatim in the spec. Full prompt text lives in the spec and in the Prompt Builders app, not here. That is deliberate: this is a register, not a second copy of the prompts.

2. Prompt Builders: the register

The Prompt Builders app is the working surface. A user types values into fields, the builder assembles the full working prompt live, and the result can be copied or handed to an agent as a JSON packet. It was generated from two canons: the Token-Swap Canon v1.1 (1,346 lines) and the AaaS System Canon v1.0 (787 lines), plus the founder-ordered general builders. The spec rule is that every option, default, and template string is copied from the canon text and nothing is invented. A null default means the canon gives no default for that field. A null options list means the canon names the field but enumerates no options.

4.1 What the two kinds are

  • Example prompt: a full prompt text. "Use this example" pulls field values from it, or it can be opened with "View full text".
  • Example output: a finished artifact produced by a prompt. It can be opened with "View" or copied with "Copy".

4.2 Hash verification

All 125 examples were seeded from the Token-Swap Canon v1.1 and the AaaS System Canon v1.0, via the 2026-11-17 extractions under ~/workspace/prompt-builders/extractions/. The extraction .txt files remain the verbatim sources of truth and were not touched by the migration. The inventory is ~/workspace/prompt-builders/examples-seed-inventory.json, with one text_sha256 per entry. Every migrated text was hash-checked against it before writing, with 0 mismatches. That is the hash verification this document claims: seeded text matches its inventory hash, 125 of 125.

4.3 The 3 ambiguous entries, kept as classified

Three entries were marked ambiguous in the inventory and kept under their assigned kind, all kind prompt:

  • seed-altar-warrior-suites-10: JavaScript builder code, not a prompt string itself. The returned template literal is a prompt, so kept as prompt.
  • seed-resale-listing-engine-02: composite of an example voice note, a system prompt update, and a sample output. Bulk is model instruction, so kept as prompt.
  • seed-n8n-modular-house-agent-02: Docker and shell setup steps for n8n, not a model instruction and not a finished artifact. No output class fits, so kept as prompt.

4.4 Rules the library enforces

  • Dedup: the key is builder id plus kind plus normalized text (trimmed, whitespace collapsed, lowercased). Adding a duplicate is refused with "Already in this builder's library." Import merges with the same rule. Seeded examples are never duplicated by import.
  • Use counts: "Use this example" adds 1 to that example's count. Viewing an output example adds 1. Viewing a prompt example's full text does not add to its count. Examples sort by use count descending, then label ascending. Every entry shows its count as "Used N times", including 0.
  • Pull rule: for each field of the builder, if the field's non-empty default, or one of its select options, appears as a substring in the example text (case-insensitive), that field is set to the matched value and saved. The status line states exactly how many fields matched and names them. If none match, the status says so plainly. A fill is never claimed when it did not happen.
  • Export and import: export downloads neuruh-prompt-builder-examples.json (format neuruh-prompt-builder-examples, version 1) with every example in the library, seeded plus user-added, with use counts. Import merges valid entries and reports added, skipped duplicates, and rejected invalid counts. A bad file never crashes the page. There is no backend. User-added examples live in the browser only until exported.

5. Prompt patterns: PMLA, SAL, Token-Swap, brief builders

Every prompt pattern in this section states what it is, what it does, its state, and its source. The first three are named patterns from the canon. The fourth is the general pattern the three founder-ordered builders implement.

5.1 PMLA: Prompt-as-Memory Loop Architecture

What it is: a framework in which a prompt is treated as memory. A 5-block prompt runs through a memory write gate into a session store, is recalled on the next turn, and is refined and run again.

What it does: the working demo runs that loop in the browser, with a hash-chained receipt v1.0 trace (Web Crypto verify per receipt) and a step-by-step F(t) = 2^(-t/h) decay calculator.

State: LIVE as a demo, and the demo is a simulation (Tier B working demo). The loop runs in the browser against a session store. It is not a production memory system.

Where it lives: live demo neuruhai.github.io/neuruh-demos/pmla-memory-loop/; local ~/workspace/pmla-memory-loop. Seed index record pmla-memory-loop, state LIVE.

Figure 2. PMLA loop. The demo is a browser simulation: the memory write gate is illustrative, the store is a session store, and the decay calculator is a step-by-step illustration of F(t) = 2^(-t/h). It proves the loop shape, not a production memory system.

5.2 SAL: Stacked Agent Logic

What it is: a prompt engineering framework for stacked agent logic. One bank item runs through six stacked stages into one platform draft.

What it does: the six stages are ingest, stack, transform, verify, queue, receipt. The implementation applies it to the 30-item content bank, with a repurpose queue view, cursor control, and a hash-chained receipt v1.0 panel. Drafts only. Nothing publishes.

State: framework IMPLEMENTED. Its demo is LIVE and is a simulation.

Where it lives: live demo neuruhai.github.io/neuruh-demos/sal-content-pipeline/; local ~/workspace/sal-content-pipeline. Seed index records sal (IMPLEMENTED) and sal-content-pipeline (LIVE, simulation).

5.3 Token-Swap: the master mechanic behind the builders

What it is: the Token-Swap Image System. A master template carries token slots (angle, tech, enhance, negative, and more). The user copies the master template, swaps tokens or entire lines, pastes the expanded prompt into the preferred model, and iterates. That mechanic is what the Token-Swap builders implement as fields: each field is a token bank, each option is a token.

What it does: it turns one canonical image prompt into a family of variants by substitution, without rewriting the prompt each time. The Modular House System (17 token banks) is the fullest expression of it in the register. The TECH Block standardizes on 16-bit color depth in the canon; the Token-Swap PDF says 12-bit RAW, and the spec keeps the canon 16-bit standard and records the inconsistency rather than hiding it.

State: LIVE, as implemented by the 13 Token-Swap builders in the register (12 LIVE, 1 DESIGNED for the capsule frame, plus the n8n agent builder DESIGNED). Source: Neuruh Token-Swap Image System, The Canonical Document, v1.1, 1,346 lines, local ~/workspace/token-swap-canonical/TOKEN-SWAP-CANONICAL.md. Live canon page: neuruhai.github.io/neuruh-demos/token-swap-canon/.

State: LIVE. Where they live: the Prompt Builders app, same live URL and local spec as the rest of the register.

7. Neuruh Prompter

What it is: a voice-following teleprompter PWA. It follows the speaker's voice word by word so the speaker never loses their place on camera. It saves scripts, persists them across reloads, supports remote control from a phone, and ingests hub takes with a SHA-256 receipt.

What it does: word-level tracking with a 14-word lookahead. Voice mode degrades on iPhone while recording (VAD degradation on iPhone is a known, stated limit, not delivered). Save flow fixed and re-verified in a live browser: Save names the script from its first line, confirms in a status line, and the entry persists across reloads. A service-worker cache trap was found and fixed: sw.js bumped to np-v3.1.0 with network-first navigation, so a fix can no longer hide behind a cached page.

State: LIVE. Version 3, 65,610 B, verified live 2026-11-10. Live MD5 of index.html at that verification: a1738142b079c9217072dd7f213cb011. Static build runs standalone; hub features need serve.py on the local machine.

Where it lives: live neuruhai.github.io/neuruh-demos/neuruh-prompter/; local ~/workspace/your_files/neuruh-prompter. Seed index record neuruh-prompter, state LIVE. Segment record: Tools and Utilities inventory item 24, and the only tool in the segment with a daily-use shape.

Price: UNKNOWN. The segment record does not set a price for the Neuruh Prompter. The Tools marketing doc states "no prices or checkout".
