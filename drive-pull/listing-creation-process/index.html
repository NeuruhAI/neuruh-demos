[The reply is a code block titled:] MASTER HANDOFF, NEURUH MOBILE RESALE INTAKE + LISTING PIPELINE

  1. PURPOSE OF THIS HANDOFF

You are taking over a project for Jeramie Hicks involving a simple mobile-first resale intake system that allows Jeramie to photograph physical items on his phone, provide minimal information, and hand the resulting structured item files to one or more AI agents that can turn those raw inputs into marketplace-ready listings.

This is not supposed to begin as a complicated SaaS application.

The core insight from the conversation was:

Build the lowest-friction capture layer first. Let the intelligence live downstream in the agents.

Jeramie regularly encounters undervalued physical assets, estate-sale material, tools, equipment, collectibles, electronics, vehicles, household items, miscellaneous resale inventory, and other things that can be monetized through marketplaces.

The operational bottleneck is not necessarily identifying that something has value.

The bottleneck is:

physical item → photos → identify → research → price → describe → organize → create marketplace-specific listing → publish → track → sell

The system being discussed should compress that workflow dramatically.

  1. ORIGINAL USER INTENT

Jeramie's request was essentially:

He wants a small system he can use directly from his phone where he can:

  1. Take/upload pictures of approximately 20 different items at once.
  2. Put those items into some kind of organized file or container.
  3. Optionally type a very short description or notes.
  4. Save the batch.
  5. Allow one of his AI agents to pick the files up.
  6. Have the agent determine what each item is.
  7. Generate marketplace listings.
  8. Generate Facebook Marketplace listings.
  9. Generate eBay listings.
  10. Potentially generate Facebook Group/community listings.
  11. Eventually make posting/listing dramatically more automated.

The emphasis is extreme simplicity during physical intake.

Jeramie should not have to stand in front of an item filling out twenty form fields.

Ideal intake looks much closer to:

Photos + 10 seconds of voice/text + save.

Everything else should be inferred, enriched, researched, generated, validated, and organized downstream.

  1. KEY ARCHITECTURAL DECISION ALREADY MADE

The first version should NOT be a full native mobile application.

The easiest practical MVP identified was:

Mobile Intake Folder + Structured Metadata + Agent Processing

The phone becomes the capture surface.

The filesystem becomes the handoff protocol.

The agents become the intelligence layer.

Example: /resale_intake/ └── 2026-08-23_estate-tools-batch/ ├── item_001/ ├── item_002/ ├── item_003/ └── ...

Each item's folder contains: item_001/ ├── photo_01.jpg ├── photo_02.jpg ├── photo_03.jpg ├── photo_04.jpg └── intake.json

Or during an ultra-lightweight first implementation: item_001/ ├── IMG_001.jpg ├── IMG_002.jpg ├── IMG_003.jpg └── notes.txt

Then agents convert the unstructured/raw intake into the canonical structured object.

  1. WHY THIS IS THE RIGHT MVP

Do not prematurely build:

• custom iOS application • Android application • giant database • complex account system • marketplace API integrations • automated posting engine • inventory ERP • microservice architecture • complicated UI • custom photo uploader • Kubernetes • another dashboard

Those may come later.

The first problem is simply:

How does Jeramie move 20 physical objects from the real world into machine-readable inventory with as little friction as possible?

The proposed answer:

iPhone + Shortcuts + iCloud Drive

Potential alternatives later:

• Google Drive • Dropbox • local Neuruh storage • Tailscale-mounted NAS • Supabase Storage • S3-compatible object storage • Neuruh Vault • private server • desktop sync folder

But iPhone Shortcuts + iCloud Drive is probably the fastest zero-development capture layer.

  1. HIGHEST-TIER VALUE OF THE IDEA

The highest-value interpretation of this project is not "an eBay listing generator."

That framing is too small.

The actual system can become:

Physical Asset Ingestion Infrastructure

The architecture converts arbitrary real-world inventory into structured digital assets.

The pipeline is:

PHYSICAL OBJECT ↓ MOBILE CAPTURE ↓ VISUAL / TEXT / VOICE INTAKE ↓ CANONICAL ASSET RECORD ↓ MARKET RESEARCH ↓ VALUATION ↓ LISTING GENERATION ↓ MARKETPLACE DISTRIBUTION ↓ SALE

That turns what looks like a simple resale helper into a potentially reusable asset-liquidity operating system.

The same ingestion protocol could eventually support:

• estate cleanouts • thrift sourcing • garage sales • auctions • liquidation lots • collectibles • trading cards • construction equipment • tools • automotive parts • motorcycles • dirt bikes • industrial equipment • farm equipment • electronics • furniture • antiques • building materials • appliances • commercial surplus • government surplus • warehouse liquidations • abandoned inventory • business closures

That is substantially more valuable than a listing writer.

  1. THE CORE PRODUCT PRINCIPLE

Separate Capture From Intelligence

The user should only provide information that cannot reasonably be inferred.

Human provides:

• photographs • optional 5-20 second note • quantity if unclear • known defects • known provenance if useful • minimum acceptable price if applicable

AI determines:

• likely object • manufacturer • model • SKU • approximate year • dimensions where inferable • material • variant • category • condition • important defects • missing pieces • comparable items • sold comps • current asking prices • sell-through likelihood • estimated market value • recommended asking price • minimum price • expected sale price • best marketplace • title • description • item specifics • tags • keywords • shipping strategy • local-pickup suitability • listing warnings • fraud/scam considerations

This distinction is important.

Do not turn AI automation into a form-filling exercise.

  1. STATUS STATE MACHINE

A standardized state machine will matter once this scales.

Recommended states:

CAPTURED ↓ QUEUED ↓ IDENTIFYING ↓ IDENTIFIED ↓ RESEARCHING ↓ VALUED ↓ DRAFTING ↓ READY_FOR_REVIEW ↓ APPROVED ↓ PUBLISHED ↓ SOLD / UNSOLD / DELISTED

  1. AGENT ARCHITECTURE

Do not necessarily create separate LLM processes for every role initially.

Conceptually, however, the pipeline should contain these capabilities.

Agent 1, Intake Normalizer

Input: photos notes metadata

Output: canonical item record

Agent 2, Visual Identification Agent

Determines:

• item category • brand • model • probable variant • distinguishing features • identifying text • labels • serial numbers • included accessories • visible condition

Outputs confidence score.

Agent 3, Research Agent

Finds:

• product documentation • original MSRP • active listings • sold listings where accessible • marketplace demand • historical pricing • variants • common failure points • collector relevance

Agent 4, Valuation Agent

Produces: market_low market_mid market_high quick_sale_price normal_sale_price optimistic_price minimum_acceptable_price

Eventually incorporate: expected_value = sale_probability × net_sale_price - fees - shipping - labor - holding_cost

Agent 5, Listing Generator

Produces platform-specific titles, descriptions, and item specifics.

Agent 6, Marketplace Publishing Agent

Creates drafts. Later: submits listings through official APIs or supported channels. Never publish without human review until a policy gate is proven.

Agent 7, Human Review / Policy Agent

Checks:

• accuracy • price sanity • prohibited-item policy • condition honesty • duplicate risk • missing information

Agent 8, Inventory / Lifecycle Agent

Tracks items after publication:

• listed • viewed • messaged • negotiated • sold • shipped • picked up • delisted • relisted

All agents should ultimately work against the same canonical record.

  1. CRITICAL ADDITION: VALUE DENSITY

The system should eventually decide whether something is even worth listing.

Define:

Value Density = Expected Net Profit / Human Minutes Required

Example:

Item A Expected profit: $15 Human labor: 30 minutes

Bad candidate.

Item B Expected profit: $120 Human labor: 8 minutes

Excellent candidate.

This allows the system to decide:

SELL INDIVIDUALLY BUNDLE SELL LOCALLY AUCTION PART OUT WHOLESALE DONATE SCRAP KEEP IGNORE

That decision engine may ultimately be more valuable than the listing-generation component.
