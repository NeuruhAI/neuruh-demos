1v1.0 as specified

Reproduced exactly as specified by Jeramie Hicks. Nothing added, nothing reworded.

  1. Before coding

    Restate acceptance criteria as a numbered, testable list. Each criterion maps to at least 1 executable check (self-test case, assertion, or script). If a criterion is not testable, say so and propose one.

  2. Implement the smallest increment

    Implement the smallest increment that addresses the next criterion.

  3. Verify with oracles, not judgement

    Run, in order:

    • syntax/lint/typecheck
    • built-in self-test harness, all cases, not just new ones
    • headless load: zero console errors/warnings, CSP violations = 0
    • domain checks: invariants, conservation laws, known analytical solutions or reference values, state source or derivation
    • a11y check (axe-core or equivalent) for UI changes

    Paste the actual command output. Never write "tests pass" without it.

  4. On any failure

    Diagnose root cause in one or two sentences, fix, rerun ALL checks (regression). Max 3 iterations per failure; then stop and report the blocker with evidence and hypotheses.

  5. Forbidden
    • weakening, skipping, or deleting a test to get green;
    • hardcoding expected outputs;
    • claiming a check ran that did not.

    Any test change must be justified explicitly.

  6. Exit report per increment
    • criteria to check to PASS/FAIL table;
    • what was NOT verified and why (mark UNVERIFIED);
    • residual risks / edge cases not covered.
  7. Fresh-context review for high-stakes changes

    For high-stakes changes: a fresh-context reviewer (subagent or new session) audits the diff against the criteria without seeing the implementation reasoning.

2v1.1 improvements

From the Neuruh estate. Each item names the lesson, the date it was learned, and the step it changes. Nothing here is invented; every date is the date the estate learned it.

  • AStep 0a, Ground truth first
    MILK lesson, 2026-11-10

    Before coding, establish where the thing lives, whether it has tests, whether it is in git, whether secrets are involved. No artifact until ground truth is established. Building from memory produces correction cycles.

  • BStep 2f, Rendered check
    Doubt-removal rule, 2026-11-14

    Read the rendered page at native size, not just the DOM. A page that loads but does nothing when touched counts as BROKEN.

  • CStep 2g, Live check
    Service-worker and browser cache trap, proven 2026-11-14 and 2026-11-15

    After deploy, reload once before testing, then verify live by curl plus MD5 byte-identical to local. A first-load failure right after a deploy is cache until proven otherwise.

  • DStep 2h, Verdict ladder
    Doubt-removal program, 2026-11-14

    jsdom verdicts are STATIC-WORKING at most, never browser-verified WORKING. Float32 rule: a raw value counts as CLEAN if it equals the expected decimal OR its float32 rounding.

  • EStep 5b, Receipt
    Receipt doctrine, canonical v1.1

    The exit report is sealed as a SHA-256 hash-chained receipt (GENESIS-first), not chat text. Receipts outrank chat.

  • FStep 3a, Stop at gaps
    Segment program, 2026-11-16

    When a source leaves a gap, stop that item, record it BLOCKED with the exact missing fact, continue only on items with explicit outcomes. Never fill a gap with an invented default, synthetic receipt, or new design presented as settled.

  • GStep 4 additions to Forbidden
    Estate lessons, 2026-10-02 to 2026-11-16
    • pasting read-tool display output back into a file (use exact-match edits);
    • announcing a fix as proven until it is proven under the failing conditions;
    • verifying counts from the first page only (verify counts over the full set).
  • HStep 6 note, reviewer independence
    Doubt-removal program, 2026-11-14

    The fresh-context reviewer also re-verifies the live URL independently, not the builder's screenshots.

Residual risks

  • The receipt writer runs in an async handler. Receipt appends must go through the promise queue, or rapid clicks fork the chain (Retardio System lesson, 2026-11-15).
  • The chain is not yet anchored on chain. Anchor root stays null until a chain and wallet are picked.

4Why this exists

The reference for this standard was a thrust-vectoring nozzle interface: pitch and yaw limits stated up front (minus 8.5 degrees to plus 8.5 degrees), live temperature and stress readouts, an IK solver whose state is visible, every actuator listed in a feature tree. The nozzle does not trust the pilot's intent. It trusts the solver, the limits, and the readouts. The Validation Loop is the same idea applied to software. Limits are stated before coding, every output is checked against an oracle, nothing ships on hope, and the result is sealed as a receipt a stranger can verify. Aerospace-grade rigor is not a metaphor here. It is the requirement: deterministic validation, not hope.
