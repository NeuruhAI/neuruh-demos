The model, stated plainly

coverage = 30% when both toggles are ON coverage = 15% when exactly one toggle is ON coverage = 0% when both toggles are OFF paper loss = property value x coverage tax savings = min(paper loss, income) x tax rate recommended property = income / coverage Test vector from the "Your Job" delivery checklist: income 250,000, tax 37%, property 1,000,000, both toggles ON paper loss = 1,000,000 x 0.30 = 300,000 tax savings = min(300,000, 250,000) x 0.37 = 92,500 recommended property = 250,000 / 0.30 = 833,333

Flagged inconsistency in the source test vector: the checklist expects about $92,500 in savings (which this model reproduces exactly) but also expects about $1.25M in recommended property. A 30 to 50% coverage range implies $500,000 to $833,333 of recommended property for $250,000 of income. $1.25M falls outside that range, so the source figure cannot be right alongside its own coverage range. This demo shows $833,333 and flags the $1.25M figure.

What was wrong in the source code

Four conflicting math versions were found in the slice: the 7/17 Flask backend used a 100% rule and had three bugs (an undefined variable, a backend key of purchase_price while the frontend sent property_value, and a block that made the recommendation echo the input); the ZIP backend used multipliers of 0.3 base + 0.2 bonus + 0.25 cost segregation; the touch script used 1.1x with recommendation equal to savings x 10; and the 3.0 HTML page used fixed mock multipliers (income x tax x 0.85, income x 2.5, income x 15) whose toggles and property value changed nothing. This demo replaces all four with the single stated model above.
