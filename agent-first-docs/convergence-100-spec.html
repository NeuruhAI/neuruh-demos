Convergence spec, Jeramie, 2026-11-15 07:00 EST

Instruction: "add in only if this keeps making our system 100x better. we dont want to take away or remove what we have hoping to eventually converge on singular autonomous outputs that are quantified and verified to match sharing to things learned, improvements and more." This spec passes that test: it is additive (nothing existing is removed), sequenced (the highest-leverage loop first, everything else compounds only after it produces numbers an independent party can recompute), and it converges on singular autonomous outputs that are quantified and verified. The explicit non-goal: the system does not become recursively self-modifying general intelligence. Improvement is limited to better-calibrated observation and forecasting under logged authority and independent verification.

1-15: Finish and harden the verified base

  • Generate a machine-readable inventory of all 178 demos with their verification date, MD5/SHA-256 of the page, and the exact interaction that was confirmed.
  • Add a CI job that re-fetches every demo URL and fails if the content hash changes without an updated verification record.
  • Extract every receipt format currently used across demos into one canonical JSON schema (v1.1) with required fields and a shared hashing rule.
  • Build a single offline verifier that accepts any demo's exported receipt chain and recomputes the hashes.
  • Add a "last verified" timestamp and verifier identity to every demo card in the hub.
  • Create a regression suite that replays the documented click sequences for the flagship Unified Chain and records the resulting receipt.
  • Pin all external CDN dependencies (Three.js, etc.) with subresource integrity hashes.
  • Publish the exact browser and interaction checklist used on 2026-11-14 so a third party can re-verify.
  • Mark every demo that still uses pure keyword banks with a visible "heuristic" badge.
  • Add an export of the full 178-item list as signed JSON whose hash is included in the next Merkle manifest.
  • Implement a simple health endpoint per demo that returns only status + content hash.
  • Document which demos share code or data so a change in one can be traced to others.
  • Add a tamper-test harness that flips one byte in a receipt and confirms every demo that claims a chain rejects it.
  • Version the working-demos page itself and include it in the on-chain anchor manifest.
  • Establish a rule: a demo may be labeled WORKING only after the interaction checklist and hash are recorded in the Done Ledger.

16-30: Layer 1, Real observation (replace keyword banks)

  • Define a typed observation schema (source, locator, retrieved_at, raw_hash, payload, schema_version) usable by any future connector.
  • Implement one narrow public connector (single county property records or one published scam-wallet list) that emits observations into an append-only log.
  • Require every observation to carry a recomputable hash of the exact bytes retrieved.
  • Add a connector test that replays a known historical payload and asserts identical hash.
  • Store observations so an independent party can re-fetch and confirm the hash.
  • Reject any observation whose schema fails validation before it enters the log.
  • Add rate-limit, cache, and error-observation types for the connector.
  • Emit a receipt for every successful and failed retrieval.
  • Surface the observation log in a minimal explorer that shows raw hash and canonical form.
  • Keep the first connector read-only and public-data only.
  • Document the exact API or bulk-file parameters so the observation is reproducible.
  • Add a human review flag on observations that match a high-sensitivity pattern.
  • Measure connector uptime and hash-match rate as a tracked indicator.
  • Do not add a second data source until the first has 30 days of stable receipts.
  • Include the observation schema version in the Merkle manifest.

31-45: Layer 2, Pre-registered forecasts and Brier scoring

  • Define a forecast record schema (forecast_id, observation_ids, type, probability, issued_at, model_version, features, receipt).
  • Require every forecast to be written before the outcome window opens.
  • Implement three narrow forecast types on the chosen public data source.
  • Add an outcome record schema that references the forecast and supplies the 0/1 result plus evidence hashes.
  • Compute Brier score over resolved forecasts and publish the number.
  • Compare every model or weight change against a constant base-rate baseline.
  • Retain an update only if Brier improves on a subsequent or held-out set.
  • Store the pre-update and post-update Brier with receipts.
  • Add a simple calibration plot (reliability diagram) export.
  • Start with a transparent scoring rule or logistic regression; do not begin with an opaque model.
  • Log the exact feature vector used for each forecast.
  • Set a minimum number of resolved forecasts (e.g., 200) before any promotion.
  • Make the Brier calculation independently recomputable from the exported log.
  • Add a "forecast issued" receipt that can be anchored later.
  • Refuse to emit a forecast if required observations are missing or unhashed.

46-60: Layer 3, Authority and gates

  • Define a minimal authority header (authorizer, scope, expiry, single-use token or equivalent, receipt).
  • Require the header on any export, alert, or weight-update proposal.
  • Implement a deterministic policy gate that can DENY or ESCALATE independently of the scoring function.
  • Log every gate decision with its own receipt.
  • Keep human approval mandatory for any action that leaves the system.
  • Add expiry enforcement that rejects stale authority.
  • Record the gate version inside the receipt.
  • Test the gate with synthetic unauthorized requests and confirm denial.
  • Surface pending escalations in a queue that matches the existing Command pattern from the Solution Swarm.
  • Make authority scope explicit (which data source, which forecast type, which time window).
  • Add a revocation list that the gate checks.
  • Ensure the gate's code hash is included in the system manifest.
  • Document the exact conditions under which the gate fails closed.
  • Do not allow the scoring model to override a gate denial.
  • Include gate decisions in the same receipt chain used by forecasts.

61-75: Layer 4, Measurable learning and promotion

  • Separate proposal of a change from acceptance of a change.
  • Require a held-out or forward-test set for every proposed scoring update.
  • Record the Brier delta and the data slice used.
  • Add a promotion receipt that links the old model version, new version, and evidence of improvement.
  • Implement automatic rollback if a subsequent window shows degradation.
  • Log every weight or parameter change with before/after values.
  • Keep a human confirmation step on the first N promotions.
  • Measure "useful escalation rate" as a secondary indicator.
  • Add a simple experiment tracker that prevents reuse of the same data for both proposal and confirmation.
  • Surface calibration drift over time.
  • Refuse promotion if the number of resolved forecasts is below threshold.
  • Include the learning rule version in every forecast receipt.
  • Test the promotion gate with a deliberately worse model and confirm rejection.
  • Publish the promotion history so an external party can audit it.
  • Limit recursion to improvement of the measurement apparatus only.

76-90: Receipts, Merkle, and independent audit

  • Unify all new receipts (observation, forecast, outcome, gate, promotion) under one chain format.
  • Add the current Merkle root of the 178 demos + new logs to every major receipt.
  • Execute one real OpenTimestamps or cheap L2 anchor of the manifest and publish the proof.
  • Build a third-party verifier (different language) that recomputes the root and checks the anchor.
  • Include the verifier's own hash in the next manifest.
  • Add a public status endpoint that returns root, leaf count, anchor txid, and last Brier.
  • Implement a one-click "verify this receipt chain" that works offline.
  • Test truncation, reordering, and content-edit attacks against the chain.
  • Anchor the Brier results periodically so calibration claims are timestamped.
  • Keep raw observation bytes (or locators) available for re-hashing.
  • Document the exact canonicalization so others can reimplement it.
  • Add a "chain valid / chain broken" badge driven by recomputation, not by a stored flag.
  • Store the anchor proof alongside the manifest.
  • Make the Done Ledger pull its evidence hashes from the same chain.
  • Require that any claim of "improved" be accompanied by the before/after Brier and the anchor reference.

91-100: Controlled broadening and finish criteria

  • Add a second public data source only after the first source has stable Brier and verified receipts.
  • Re-run the full observation → forecast → outcome → Brier loop on the new source before merging.
  • Keep financial-crime and influence patterns at the typology level; route any concrete finding to official channels only.
  • Add a contract/schema check so modules accept only messages they are authorized to process.
  • Measure end-to-end latency from observation to receipted forecast.
  • Establish a kill switch that halts new forecasts without deleting history.
  • Finish criterion: 178 demos still verify, one real anchor exists, one data source produces calibrated forecasts, and an independent party can recompute the receipts and Brier.
  • Finish criterion: every promotion has a recorded Brier improvement on data not used to propose it.
  • Finish criterion: the simulation badges are removed only where the above evidence exists; elsewhere they stay.
  • Explicit non-goal: the system does not become recursively self-modifying general intelligence. Improvement is limited to better-calibrated observation and forecasting under logged authority and independent verification.

These 100 upgrades are sequenced so an agent can execute them against the existing 178 working demos and the documented ledgers. The highest-leverage starting subset remains the observation schema + one public connector + pre-registered forecasts + Brier gate. Everything else compounds only after that loop produces numbers that an independent party can recompute.
