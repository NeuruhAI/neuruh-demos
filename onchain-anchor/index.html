2. What an anchor is, and what it is not

What it is

  • A timestamped claim of authorship. The Merkle root commits to the exact bytes of every artifact listed below, as they existed on the anchor date.
  • It proves existence of bytes at a time, and nothing more. Given any artifact, hash it, find it in the manifest, and walk its Merkle path to the root. No trust in Neuruh is required, only SHA-256.
  • One anchor for the whole estate. A single root covers all 187 sites, the seven papers, the codex, the maps, and the ledgers, plus the anchor's own tooling (the page, the verifier, and the build scripts are leaves in this manifest too).

What it is not

  • Not proof of truth. A hash says these bytes existed; it says nothing about whether their claims are true.
  • Not by itself a court ruling on legal ownership. It proves a hash existed at a time as published by this anchor. It does not settle a legal dispute on its own.
  • Not proof of ongoing liveness. A hash proves the bytes as fetched on the anchor date. A site can change or go down afterward.
  • Not a chain write yet. This page is the prepared anchor (manifest + roots + verifier). Nothing has been written to any blockchain until the transaction in section 7 is made.
  • Not a substitute for the artifacts themselves. Keep the originals. A hash without the artifact proves nothing about its content.

5. How the tree is built

Leaves are SHA-256 of the canonical JSON of each manifest entry (keys sorted, no whitespace, UTF-8). Parents are SHA-256 of the concatenated raw 32-byte child hashes. An odd level duplicates its last node. The root is the single hash at the top. The same rule is used by the Python builder and by this page, so the page's recomputation is an independent check of the published root.

Leaf order is locked: the 187 sites in registry order, then the papers, then the documents, then the ledgers, then the self entries (page, verifier, manifest-content, build tools, retained v1 artifacts). Re-running the builder with unchanged inputs produces the same order.

Published parent test vector: given two child hashes, the parent is SHA-256 of their raw 32-byte concatenation. See test-vectors.json (vectors: empty tree, single leaf, 2/3/4/5 leaves, tampered leaf, tampered sibling, canonicalization). Full byte-level rules: CANONICALIZATION.md.

The v2 manifest publishes two roots: the estate root (204 estate leaves, baked into this page) and the full root (estate + self leaves). The page recomputes both; both must match. A file cannot contain its own hash, so the manifest commits to itself with a manifest-content leaf (the SHA-256 of the canonical entries array) and publishes its own file hash beside it in manifest-v2.sha256. The v2 page, verifier, and tooling are leaves in the v2 manifest; the v2 manifest file itself will be a leaf in the next manifest (v3).

Option A — OpenTimestamps (Bitcoin-anchored) — $0 — recommended first step

Cost: $0. No account, no API key, no wallet. The file never leaves your machine; only its hash is submitted to public calendar servers, which aggregate many hashes into a Merkle tree and anchor that tree's root in a Bitcoin OP_RETURN transaction.

Script: ots_anchor.sh — stamp → wait → upgrade → verify, with the expected output at each step. Run it only after Jeramie approves (it checks for anchor-approval.txt first).

  1. pip install opentimestamps-client
  2. ots stamp manifest-v2.json — creates manifest-v2.json.ots (pending proof).
  3. Wait a few hours for the calendar servers to anchor to Bitcoin, then ots upgrade manifest-v2.json.ots.
  4. ots verify manifest-v2.json.ots — checks the proof against Bitcoin (the command-line verifier needs a local Bitcoin node; the opentimestamps.org website verifies in the browser without one).
  5. Keep manifest-v2.json and manifest-v2.json.ots together, and publish the .ots file alongside the manifest. The .ots file will live at ~/workspace/onchain-anchor/manifest-v2.json.ots and next to the manifest on this site. Verify it at opentimestamps.org.

Failure modes: calendar server slow or unreachable (upgrade says "pending" — wait and retry; the .ots file stays valid); CLI verify needs a local Bitcoin node (use the website instead). Sources: opentimestamps.org; OpenTimestamps client README. Checked 2026-11-15.

Option B — Solana memo — about $0.00025

7. Receipts and audit

Every verification on this page produces a local receipt (inputs, root, path result, timestamp, verifier version). Receipts chain: each carries prev_hash (the previous receipt's hash, GENESIS for the first) and receipt_hash (SHA-256 of the canonical receipt body). The log is append-only and exportable as JSONL. verify_receipts.py recomputes every receipt hash from its body and checks the chain independently.

Self-anchoring: this page, the verifier (verify.js), and the build tools are leaves in this manifest (kind tool and manifest). The page's own hash is committed in the manifest it verifies. The manifest's own file hash is in manifest-v2.sha256 and in status.json.

Verify this page without trusting the host: (1) download manifest-v2.json and verify_standalone.py (one file, Python 3 stdlib only, no network). (2) Run python3 verify_standalone.py manifest-v2.json --root — it recomputes the root from the manifest and compares it to the published root. (3) Run it with --hash <sha256> for any artifact. No Neuruh code and no live site is trusted in that check; only SHA-256 and the manifest bytes you downloaded.

Audit script: audit_anchor.py fetches the live page, the live manifest, and the live status file and confirms page root == recomputed root == anchored root (the third check reports BLOCKED until a chain write exists).

Build receipt: the manifest carries a build receipt (who ran the builder, when, and the hashes of its inputs). The manifest's verifier field pins the verifier code: version 2.0.0, file verify.js, with its SHA-256.

Superseded entries: the v1 manifest and v1 page are retained as leaves with status superseded. Their old hashes stay verifiable; the v2 entries supersede them. See manifest-v1.json and the changelog.

Cross-reference: artifacts here that are AI-generated (the demos, the papers) are subject to CRUCIBLE-style citation and eta checks where they apply; see the CRUCIBLE demo. Future CRUCIBLE and swarm receipts will carry this anchor's root (anchor_root) so a receipt can be checked against the anchor. Archive plan: every manifest version, its .ots proof, and a snapshot of this page are kept in ~/workspace/onchain-anchor/ and in the NeuruhAI/neuruh-demos repo under onchain-anchor/; nothing is deleted, and each new version is recorded in the changelog.
