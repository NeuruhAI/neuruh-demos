Stage 2: Signal verification (Section 5)

A detected signal is not a worked signal. It passes four checks, in order, plus Check 2.5. Fail any one and it is parked with the reason recorded, not silently dropped. Chaff classification is a first-class output: the pipeline logs chaff with the same care as signals, because the chaff log is what proves the filter works. A run that finds only chaff is a successful run, not an empty one.

Stage 6: Learning (Section 9)

The Nexus meta-feedback loop is the design: analyze success and failure patterns of cross-domain intersections, broadcast algorithm updates back to the engines. The pipeline implements it in three concrete steps:

  1. Outcome writes back to the signal record. A reply, booking, decline, or stop updates the entity record and the recipe row. A decline on a probate signal lowers that recipe's weight for that entity type; a booking raises it. Weights live in landos-engine/app/scoring.py and are re-seedable; the pipeline proposes weight changes, it does not apply them silently.
  2. Chaff writes back to the filter. A topic classified as chaff three times in a week gets a standing chaff entry, so future runs skip it without a full audit. The chaff log is reviewed weekly; a standing entry is removed only by his call.
  3. Content writes back to the bank. Every composed piece that closes a loop (reply or booking) is added to the content bank as a proven template. Every piece that fails verification is logged with the reason, so the Architect Agent does not repeat the failure.

What learning is blocked on today: the reply watch is blind (no outcome data from Messenger), the data spine is down (no live scoring store), and there is no measured baseline. Learning is DESIGNED, not running. The pipeline records outcomes to the local ledger until the spine returns, so the learning step has data waiting when it does.

Daily runbook (Section 14, one run, in order, with gates)

Step 0, operator checklist (manual, daily, before the run). Morning Zero-Feed Lock: first 90 minutes after waking on physical movement or deep build work, no browser. Chaff Flare Check: identify today's number one boosted outrage story, log it as Noise, do not click or comment. Ship One Hard Artifact: one verifiable unit of value (see step 12). High-Trust Touchpoint: 15 minutes with a real human inside the local radius or Dark Forest network.

  1. Health gate (Stage 0). Check each channel state. Skip down channels. Log skips.
  2. Intake (Stage 1). Pull-only search across the source registry. Write signal records. Apply source-health multipliers. Do not open an algorithmic feed.
  3. Chaff check (Stage 2, Checks 1 and 2). Materiality test, then velocity audit. Quarantine anything at 10/10 saturation. Log chaff.
  4. Verify (Stage 2, Checks 3 and 4). Entity resolution, consent and DNC state. Park failures with reasons.
  5. Bank check. Before composing, check the content bank and the doomer-bridge articles. Repurpose if covered.
  6. Compose (Stage 3). Content Router picks the template. Intake, Architect, Asset Generation, Assembly run. Content verification: sourced numbers with audit dates, no PII, exactly one CTA.
  7. Queue (Stage 4). Outreach Agent routes and drafts. Cold first-touch goes to his approval queue. Nothing sends in this step.
  8. Approve. He approves, edits, or kills each queued draft. Approval is per draft, not per batch.
  9. Send (Stage 4). Only approved drafts, only on channels whose send-enable flag is YES, inside the pacing budget, inside 07:00 to 22:00 Detroit.
  10. Receipt (Stage 5). One hash-chained receipt per touch. Record the outcome when it arrives. Silence is recorded after the nudge window, not assumed.
  11. Learn (Stage 6). Outcome writes back to the signal record and the recipe row. Chaff writes back to the standing log. Proven content writes back to the bank.
  12. Ship one hard artifact. The run is not complete until one verifiable unit of value exists: a code commit, an underwritten asset, an SOP, a physical repair, a composed piece with a receipt, a queued draft batch, a verified signal set with receipts, or a receipt chain. This is the manual's definition plus the pipeline's receipted outputs. This is the 1:3 ratio enforced.

Run log (one line per run): date, signals pulled, verified, chaffed, content composed, queued, sent, replies, bookings, declines, stops, artifacts shipped. The log lives with the outreach ledger until the spine returns.

Materiality rubric (Verification Check 1)

Three yes/no questions, each with the source line that supports it. Pass is at least one yes. Fail is zero yes, classified as chaff.

  1. Does this signal alter statutory law?
  2. Does this signal alter capital allocation?
  3. Does this signal alter the 50-mile radius?

Velocity metric (Verification Check 2)

Velocity is the count of distinct posts or threads on a topic across the monitored feeds in a 6-hour window, against the 30-day baseline for that topic. Saturation 10/10 is velocity at or above 3x baseline AND present in 3 or more feeds simultaneously. A chaff flare is a spike above 3x baseline with 0 percent local materiality. The 3x, 6-hour, and 3-feed values are PROPOSED (R5).

Signal state machine

States and allowed transitions. A signal is in exactly one state at a time. Nudge cap: 3 warm, 2 cold. Spacing 48h. Window 07:00 to 22:00 Detroit. followup_due is now plus 48h (warm) or plus 72h (cold).

Claim lifecycle (from the followup protocol canonical spec)

States: open, nudged, escalated, closed. Open is a reply sent, waiting, with followup_due set. Nudged is one follow-up sent after no response; the claim returns to open with a new followup_due until the cap is hit. Escalated is a response with interest, a question, or a buying signal; report the thread link to Jeramie in chat the same day; escalated claims stop nudging and a human owns them. Closed is stop or decline received, cap exhausted, thread dead after caps, or channel leg died; never touch again unless the other party messages first.

Claim schema fields: thread_url (dup-protection key), reply_url, owner, by (writer job id), time (ISO), followup_due, warm (true/false), nudges_used, nudge_cap (3 warm, 2 cold), status, channel.

Per-channel claim files, all under ~/workspace/goals/start-50-qualified-sales-conversations-from-outbound/hidden_files/: X is x-reply-claims.json. Facebook comments and groups is fb-claims.json. Messenger DMs is messenger-claims.json. Instagram and Threads is social-claims.json. BiggerPockets is bp-claims.json. TikTok is tiktok-claims.json (in the publish-30-short-videos goal hidden_files). YouTube is youtube-claims.json (same goal hidden_files). Substack is substack-claims.json. Webinar is webinar-claims.json. Offer and checkout is offer-checkout-claims.json.

Duplicate-writer protection: before posting any reply, read the channel's claim file. If thread_url appears with time less than 24h old, skip it. After posting, append a claim immediately. No exceptions.

Estate-reply-watch threads: the estate playbook overrides. Cold estate threads get no unsolicited nudges. Closed and nurture threads are never messaged. Claims on estate threads exist for duplicate protection and escalation tracking only.

First-touch drafts held for approval get no claim until he approves and something is sent.

Escalation path

When a gate fails mid-run (lock, rate limit, checkpoint, sync failure), the run stops for that channel, the skip is logged with the error, and the failure is reported to Jeramie in chat the same day. No silent failure. No retry loop in the same run.

Baseline procedure (lift measurement)

The next 20 single-domain touches (Phase 1 real-estate only) are measured for reply rate and booking rate before any compound touch is measured. Lift equals compound rate divided by single-domain rate. Until 20 single-domain touches exist, no lift number is reported anywhere.

Pull failure rule

After 3 consecutive failed pulls, the run stops attempting the pull and reports the failure to him the same day. Retry is once per run. No silent retry loop. The 3-strikes value is PROPOSED (R26).

Queue data model

The outreach queue lives in the outreach ledger (~/workspace/goals/start-50-qualified-sales-conversations-from-outbound/hidden_files/outreach-ledger.md) and the per-channel claim files above. The signal store is pipeline-signals.md in the same hidden_files directory, one JSON record per line, Section 4 schema. The first run creates it.
