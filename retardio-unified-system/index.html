Retardio Unified System v1

One promptable interface over the measurement loop, receipts, Brier gate, and connectors. It scores transactions and entity patterns (typologies) from public records. It does not score people.

SIMULATION — NOT YET ANCHORED. Browser-local static page. No data leaves this page. No wallet, no chain write, no spending, nothing posts, nothing sends. Receipts are real SHA-256 computed in this page; the system is not yet connected to a live feed, and no Brier exists yet.

What this system is not

  • It does NOT do probabilistic corruption scoring of individuals.
  • It does NOT rank private individuals as “probable corrupt actors.” No “high-ranked” individual list exists and none will be built.
  • It does NOT do remote surveillance. There is no live monitoring of people, no location tracking, no private-data collection.

What it does: it reads public records (county parcels, entity filings, court dockets, published lists), turns them into hashed observations, issues pre-registered forecasts about transaction patterns (rapid flips, entity clusters, all-cash new-entity purchases), and scores those forecasts later with Brier. A concrete finding is routed to official channels only: FBI IC3 (ic3.gov), FTC ReportFraud.ftc.gov, CFPB, the state attorney general, FinCEN via a financial institution, IRS Criminal Investigation, or local law enforcement. No private “resolution” mechanism substitutes for official process. SARs are filed by financial institutions, not by this system.

How to read this page. Sections 1–4 are the concrete package: exact schemas, the scoring rule, the fields, and the connector registry. Section 5 is the working promptable interface: type a prompt (or click an intent) and the system routes it through the governed flow, returning a result with receipt IDs and the current Brier. Section 6 is the session receipt log. Sections 7–8 are the conflicts and gaps, stated plainly instead of reconciled away.

1. Exact JSON schemas

All four records share the same chain discipline: prev_hash links to the prior record (GENESIS for the first), and receipt is a SHA-256 over the canonical record. schema_version is 1.0 throughout.

1.1 Observation

{
  "observation_id": "sha256 of canonical form",
  "schema_version": "1.0",
  "source": "st_joseph_county_arcgis | in_sos | court_docket | published_scam_list",
  "source_locator": "exact query, layer, objectid, or URL + params",
  "retrieved_at": "2026-11-15T12:00:00Z",
  "raw_hash": "sha256 of exact bytes retrieved",
  "entity_type": "parcel | deed | llc_filing | judgment | wallet_cluster",
  "payload": { /* source-specific fields, see §3 */ },
  "prev_hash": "GENESIS or prior observation_id",
  "receipt": "sha256 of this entire object after canonicalization"
}

1.5 Canonicalization rule (used before every hash)

Sort keys recursively. Collapse whitespace in strings (trim, collapse internal runs to one space). Lowercase strings. Render whole numbers as integers. UTF-8. No trailing newline.

canonical(v):
  null        -> "null"
  array       -> "[" + join(",", canonical(each)) + "]"
  object      -> "{" + join(",", sorted keys as JSON + ":" + canonical(value)) + "}"
  string      -> JSON( trim, collapse whitespace, lowercase )
  number      -> integer as-is, else shortest decimal
  boolean     -> "true" / "false"

1.6 Receipt self-reference — resolution

Conflict, resolved by definition, not by re-hashing. The schema says receipt is the SHA-256 of “this entire object after canonicalization,” but the receipt field is inside the object. A hash cannot include itself. The resolution used everywhere on this page: receipt = SHA-256 of the canonical object with the receipt field omitted, then attached. The loop’s forecast receipts already follow this resolution (its verifier deletes receipt before hashing). The loop and this page agree on the resolution; they differ on canonicalization (see §7, conflict 2).

Try it: the “Verify session log” button in §6 recomputes every receipt this page issues using exactly this rule.

2. baseline_v1 — the transparent scoring rule

Fixed on 2026-11-15. No learned weights yet. The rule is a stated assumption, not a measured rate. Every probability is issued in advance and scored later.

2.1 baseline_v1 (unified, 2026-11-15) — the rule this page runs

def baseline_v1(features):
    p = 0.15  # base rate prior
    if features.get("llc_owned") and features.get("entity_age_days", 999) < 90:
        p += 0.25
    if features.get("entity_age_days", 999) < 30:
        p += 0.15
    if features.get("prior_transfer_count_365d", 0) == 0:
        p += 0.10
    if features.get("consideration", 0) > 100000 and features.get("consideration", 0) < 500000:
        p += 0.05
    return max(0.01, min(0.95, p))
The 999 default is wrong and is NOT implemented. The pseudocode above defaults a missing entity_age_days to 999 (unknown treated as old). That silently converts missing data into evidence. This page implements the refusal path instead (convergence item 45): if a required feature is missing, the rule refuses to emit and shows the reason. The pseudocode is reproduced verbatim above because it is the source; the implementation below it is the correction. See §7, conflict 4.

Required features for the unified rule: llc_owned, entity_age_days, prior_transfer_count_365d, consideration. Rapid-flip forecasts use this probability with a 180-day window. Outcome = 1 only if a subsequent deed on the same parcel appears inside the window with consideration ≥ 1.5× prior. All other cases = 0 when the window closes.

Enter features and the rule computes the probability. Leave a required field blank to see the refusal.

  prior                                0.04

Baseline name collision (conflict 1). Both rules are named baseline_v1 and both were fixed on 2026-11-15, but they are different rules: different prior (0.15 vs 0.04), different features (entity age / transfer history / consideration band vs consideration / acreage), different clamp ([0.01, 0.95] vs [0.01, 0.50]). This page labels them distinctly — baseline_v1 (unified, 2026-11-15) and baseline_v1 (loop, 2026-11-15) — and the loop’s rule is NOT overwritten. The loop’s 20 issued forecasts keep their receipts under the loop rule. A future promotion must rename the rule (e.g. baseline_v2) rather than reusing the name for a different rule.

5. Promptable interface — the unified system

One entry point. Type a prompt (or click an intent). Internally it routes through the governed flow: intent parser (narrow, schema-constrained) → authority check → connector(s) → observations → forecast emitter → outcome coder → Brier calculator + promotion gate. Every step writes to the same hash-chained log (§6). Every result returns receipt IDs and the current Brier.

Authority, as it stands. The authority model for prompts (Layer 3) is not yet built, so this page runs in a restricted mode: reads and local computations run freely; anything that would leave the system (an alert, a report draft, an export beyond this browser) is held by the human-approval gate and is not executed. There is no authority header yet, so there is no way to authorize an external action from this page. That is the safe default, not a missing feature to work around.

9. Hosting options and the autonomous loop

9.1 Hosting options

Option A — local
Fully local / browser + local files (current Retardio style). This page. No server, no data leaves the browser.
Option B — split
Single hosted read-only explorer + local writer. The public can verify; only the local writer appends.
Option C — hosted log
Hosted append-only log with a public verifier. Still no private data; the log holds public-record observations and receipts only.

9.2 Autonomous execution loop (highest form that stays safe)

  1. Scheduled or triggered ingest of the approved public sources.
  2. Automatic forecast emission on new observations (refusing when required features are missing).
  3. Automatic outcome coding when deterministic rules can fire.
  4. Automatic Brier update.
  5. Automatic rejection of non-improving rule proposals.
  6. Human gate on: new data-source addition, first live (non-retrospective) batch, any external report, any rule promotion that passes the Brier test.
  7. Kill switch that stops new forecasts without deleting history (§5).
  8. Every cycle produces a receipted summary.

The loop is autonomous only inside the governed boundary: public data in, receipts out, human approval on anything that leaves the system. It is not recursively self-modifying general intelligence. Improvement is limited to better-calibrated observation and forecasting under logged authority and independent verification.
