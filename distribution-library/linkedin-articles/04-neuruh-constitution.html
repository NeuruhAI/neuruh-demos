The Reward Is the Problem: Why I Stopped Training Agents to Win

Most AI agents are built to chase cookies. Give them a reward function, point them at a goal, and watch them find the cheapest way to look like they succeeded. That is not intelligence. That is a raccoon in a dumpster.

I spent two years building agent systems before I put words to this. The whitepaper I wrote recently lays out the full technical case, but here is the version that matters for anyone building with agents in production.

The core claim: stop optimizing for reward. Start minimizing surprise.

Reinforcement learning trains models to maximize a score. In practice, this produces mode collapse. The agent finds one pattern that earns the reward and repeats it until the work goes mediocre. Anyone who has watched a coding agent ship the same broken fix three times in a row has seen this happen. The agent is not confused. It is doing exactly what it was trained to do: collect the cookie as cheaply as possible.

Active Inference flips the objective. Instead of chasing a score, the agent acts to reduce the gap between what it expected and what actually happened. Prediction error becomes the signal. When the agent's model of the world is wrong, it feels it. When the terminal returns a stack trace the agent did not predict, that is not a failed reward. That is information, and the agent updates.

This is not philosophy. It is a practical difference in how agents behave when they hit friction. A reward-chasing agent retries the same broken approach. A surprise-minimizing agent stops, re-reads the environment, and changes strategy. One loops. The other learns.

Architecture replaces anatomy

Here is the second claim, and it is the one that changed how I build.

Most of the industry is trying to make better models. Bigger weights, better steering vectors, more RLHF. That is anatomy work. It is trying to improve the brain.

I think the leverage is in the architecture around the model. The orchestration, the constraints, the verification loops. A mid-tier model inside a tight Plan-Act-Verify loop will outperform a frontier model running on vibes. I have watched this happen on real work, not benchmarks.

The loop is simple. Plan: the agent writes out what it intends to do before touching anything. Act: it executes against the real environment, not a simulation of it. Verify: the environment talks back through terminal output, test suites, compilers. If the result does not match the plan, the agent goes back to planning. Nothing ships until the environment confirms it works.

This is what I mean by "the environment is the memory." The agent does not need to remember everything in its context window. The terminal, the test suite, the compiler, these are external, authoritative, and always current. Reading them is cheaper than remembering. Most production failures I have seen come from agents that stopped checking the environment and started trusting their own summaries.

The governance layer is the product

Here is where most agent demos die: the moment someone asks what happens when the agent does something wrong.

If your agent can spend money, move data, or touch production, you need more than a prompt that says "be careful." You need architectural constraint. In my systems, consequential actions go through verification gates. Micro-decisions can flow. Anything above a threshold requires proof of necessity before the state machine allows the transition.

The pattern I use: every machine action leaves a receipt. Who, what, when, why, input, output, authority, provenance. This is not audit theater. It is the mechanism that makes the system insurable, debuggable, and trustworthy enough to actually deploy. The receipt is what lets a human look at what the agent did and understand it without replaying the entire run.

I also build kill switches at the state machine level, not the prompt level. A prompt-level instruction can be talked around. A binary state machine that freezes the wallet is physics, not persuasion. When I say governance, I mean constraints the agent cannot argue with, not guidelines it is asked to follow.

What this looks like in practice

I run DeedSonar, a real-estate intelligence system, on these principles. It ingests county parcel records, runs signal detection, and ranks opportunities. Every lead carries provenance: which records, which signals, which recipe produced it, when. If a ranking is wrong, I can trace it to the exact input. That is the receipt layer doing its job.

I also run a recipe system with 30 canonical patterns for turning public records into qualified opportunities. Each recipe is a repeatable, machine-readable acquisition pattern. Not a prompt template. A recipe that encodes what to look for, how to verify it, and what evidence counts as proof.

The SWARM work is the coordination layer: multiple agents working in parallel, each with bounded authority, each leaving receipts. This is where it gets real, and it is also where I am most honest about the current state. The architecture exists. The deployment exists. Full continuous autonomous operation does not, and I will not claim it until the receipts prove it.

The shift I am asking you to make

Stop being a typist. Start being an architect.

The typist writes prompts and hopes the model figures it out. The architect designs the loop: what the agent is allowed to do, what it must verify, where the human gates are, what evidence it must produce. The typist optimizes the words. The architect optimizes the physics.

This is the transition I see happening across the industry. The syntactic era was about model capability. The agentic era is about context engineering, orchestration, and verification. The winners will not be the people with the best prompts. They will be the people with the tightest loops.

Eliminate drudgery, complexity, and the blank page. That is the mission. But do it with receipts, or do not do it at all.
