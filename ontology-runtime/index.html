Ontology Runtime

The Unified Ontology and World Landing Codex, executed for real. The demo simulated an ontology in the browser. This runtime seeds it, lands Worlds through it, runs the metabolism loop, halts on invariant breach, and persists every receipt in SQLite with a hash chain.

What this is not. This is a working single-node runtime, not production. Still DESIGNED, not built: no Kafka or NATS event bus, no Temporal orchestration, no IAM or RBAC, no async notification bus for founder gates, no multi-tenant auth, no hosted deployment. The store is one SQLite file. The founder gate is approved over HTTP with no signed approval. Do not call this production ready.

The loop runs two full cycles in the demo, and in this runtime: nothing exits without an outcome returning. The Outcome node records observed reality, Memory / Calibration / Capability registers a capability on the node, and New Possibility opens a child node that becomes the next cycle's input.

04What was built

  • ontology_runtime/codex.py: the real Codex data: 13 invariants, 7 questions, 7 tests, 9 scale levels, 11 landing steps, 8 metabolism nodes, 7 bloom gates, 4 candidates, 7 injectable faults.
  • ontology_runtime/models.py: Pydantic models for the canonical_node shape exactly as the Codex states it, with the five-stage state discipline.
  • ontology_runtime/store.py: SQLite persistence: append-only event log, node snapshots, founder gates, invariant records, hash-chained receipts with chain verification.
  • ontology_runtime/seeder.py: genesis: invariants, root Universe, candidate Worlds, the semantic zoom object (one node_id at nine levels).
  • ontology_runtime/runtime.py: execution engine: landing protocol with founder gate suspend and resume, metabolism loop, bloom ladder, invariant halts, semantic zoom.
  • ontology_runtime/api.py: FastAPI surface: /seed, /worlds, /nodes, /land, /gates, /metabolism, /bloom, /zoom, /faults, /invariants, /receipts, /chain/verify, /codex, /health.
  • tests/: 28 tests covering state discipline, invariant halts, metabolism closure, the Seven Questions gate, founder gate suspend and resume, bloom holds, semantic zoom, persistence across restart, and the receipt hash chain.
  • scripts/run_e2e.py: the end-to-end execution that produced the receipt below, including the restart proof.

Run it locally: python -m venv .venv && .venv/bin/pip install -r requirements.txt && .venv/bin/python -m pytest tests/ -q, then .venv/bin/python scripts/run_e2e.py. Serve the API with .venv/bin/uvicorn ontology_runtime.api:app --port 8471.

06What is still missing for production

  • Event bus: the receipt log is one SQLite file. A live multi-agent deployment needs a durable broker (Kafka, NATS) so external agents stream outcomes back automatically.
  • Orchestration: no Temporal or equivalent. Long-running landings suspend on a founder gate in SQLite, but there is no durable workflow engine resuming them across process restarts.
  • Identity and authorization: no IAM, RBAC, or signed capability tokens. The founder gate is approved over plain HTTP with a name string. A rogue caller can approve any gate.
  • Notification bus: a held founder gate waits silently. There is no Slack, SMS, email, or approval UI dispatching it and resuming on reply.
  • Verification runners: the demo flips gate evidence by hand. A live system needs automated verification (tests, schema validators, webhook listeners) promoting observed to verified.
  • Deployment: no hosted deployment, no backups, no monitoring. One file on one machine.
