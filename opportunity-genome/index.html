1. How it works

This demo has three working tools. The genome composer builds a genome profile from an OpportunityCase by selecting traits and fields across domains. Each saved change creates a new version, v1, v2, v3, and so on. The cross-domain field mapping tool maps a field from one domain to another in an editable table, and validation checks that every mapped field has a source and a target. The genome viewer renders the current genome as a readable profile card with its version, parent case ID, and trait list.

The pipeline position is a source claim from the runtime scoping source: source to LandOS ingest to property and entity resolution to LandOS evidence to independent recipe memberships to OpportunityCase to Opportunity Genome snapshot to rank and next best evidence to investigation to underwriting to Sentinel and court to governance to sole CRM writer to DeedSonar to human and operator to outcome. That pipeline is a source claim, not a verified live pipeline in this demo.

What this is not

  • It is not a genome schema file. No such file exists in the sources.
  • It is not an OpportunityCase schema or store. No such schema or store location exists in the sources.
  • It is not a running system, a server, or a database. All state lives in this page and in the share link hash.
  • It is not a second case identity. A genome is a derived view attached to a case, never a second case identity. The parent case ID stays the identity. The genome version is only a snapshot number.
  • It is not canonical. The schema on this page is proposed by this demo, explicitly, and must not be quoted as Neuruh canon.
  • It does not depend on anything live. It depends, in the sources, on the unbuilt Organ Manifest and on frozen contracts, neither of which exists.

            9. Try-it walkthrough

            1. Check 3 traits in the composer: property identity, ownership context, and evidence. The completeness meter should read 30 percent, 3 of 10, with 7 fields missing.
            2. Click Save snapshot. The version should move from v1 to v2.
            3. Check ranking, then click Save snapshot again. The version should move to v3.
            4. In the diff tool, pick A v1 and B v3 and click Compute diff. Added should be 4 traits, removed 0.
            5. In the mapping tool, click Add mapping row, leave the target field empty, and click Validate mappings. It should FAIL and name the row.
            6. Fill in the target field and validate again. It should PASS.
            7. Click Load land-parcel genome, then Generate share link. The link restores that exact genome on load.

            10. Honest gaps

            • No genome schema file exists in the sources. No JSON schema, no table definition, no field types, and no versioning rules were found. The field list and version rule on this page are proposed by this demo.
            • No OpportunityCase schema or store location exists in the sources. Whether the case lives in Supabase, Postgres, Notion, or elsewhere is UNKNOWN in the runtime scoping source.
            • No cross-domain field mapping exists in the sources. Which fields are shared versus domain-specific for resale, defense, tax, creator and IP, and founder systems is UNKNOWN in the runtime scoping source.
            • No computation owner exists in the sources. Which service recomputes the snapshot, and on what trigger, is not specified.
            • The Organ Manifest does not exist. The runtime scoping source says no manifests are written for any organ, and until a manifest exists the organ mask concept is meaningless in the related N-Cell paper.
            • The frozen Opportunity Genome and Organ Manifest contracts against the receipt and event schemas are not frozen. They do not exist as frozen contracts in the sources.
            • No second vertical is implemented, so cross-domain behavior is unproven. The dossier source claim says a second vertical would be the decisive proof that this is a reusable kernel rather than a property app.
            • The SREIC blueprint page demo noted as missing in its own snapshot: capital constraints, buyer demand, development transforms, strategy underwrites, execution receipts, and economic outcomes. This demo does not supply them either.
            • The sources disagree or duplicate in places, flagged below, and this demo does not silently resolve those disagreements.
