2. The corpus: the asset

Built by build_corpus.py from the 1,117-record library (Nov 20 refresh), the Obsidian vault, and full text behind local paths. Re-runnable: re-run it after any vault re-seed and it rebuilds from the current index. Exact counts, counted by the Qwen2.5 tokenizer, not estimated.

What was excluded, and why

  • 6 duplicate seed records: same record id appearing twice in the index.
  • 1 vault doc excluded for a secret pattern: a session archive note matching the secret scan (name only: 11-Notion/HQ-Hub/Session-Archive/hq-sa-claude-brain-dump-april-4-2026-full-system-audit-execution-structure-code-delivery.md). The secret scan runs before the per-doc cap; the exclusion is recorded in corpus_exclusions.json.
  • 147 vault files skipped as seed local-path targets: vault files that are the local full-text source for a seed record, already covered by the seed doc (dedup, not loss).
  • 16 duplicate vault docs: same content hash, different path.
  • 1 vault doc too short: under 200 characters after cleaning.
  • Per-doc cap 200,000 characters: applied after the secret scan, so no long doc is silently truncated into the corpus.

Known cleaning limitation: some doc text includes coordinator annotation notes (e.g. "No slice located the file"). Those are true record content, not errors, but they are noise in training text. A future corpus pass should strip annotation lines. It does not block the smoke run or the RAG sidecar.

3. The model choice: Qwen2.5-0.5B, with the memory math

The training target is Qwen/Qwen2.5-0.5B (494,573,440 parameters as loaded). The stretch goal is Qwen2.5-1.5B. Bonsai used Qwen2.5-3B; that choice does not fit fine-tuning on 8 GB of RAM, which is why this program does not use it.

Why transformers plus peft, not Unsloth: Unsloth is CUDA-optimized. It buys nothing on Apple Silicon or CPU, and it adds a dependency that does not run on the target machine. Transformers plus peft is the portable standard and it runs on both this VM and the Mac. Why LoRA, not full fine-tuning: full fine-tuning of even the 0.5B model does not fit 8 GB. Why not full pretraining: impossible on $0 compute. The corpus is 16M tokens; a real pretraining run needs billions. LoRA on the 0.5B is the only method that fits the hardware that exists.

4. The RAG sidecar: the usable system, proven here

The retrieval sidecar is built and proven on this VM. It is a FastAPI service over a SQLite FTS5 full-text index of the 40,919 corpus chunks. No GPU, no language model, no spend. It answers questions grounded in the corpus with a citation per answer. This is the system that powers Obsidian "ask questions" right now, while the trained model is still ahead of us.

Ranking uses title boosting (all question terms in the title, or the longest term in the title) plus per-document dedup, so the best source wins instead of the most-mentioned one. Lesson recorded from testing: vague questions return the most-mentioned docs; precise questions return the definition. The API: POST /ask with {"question": "..."} returns the answer text and its source record. Run it: uvicorn app:app --port 8472 from the program folder.

5. The fine-tune pipeline: built here, smoke-proven, run on the Mac

The pipeline is four scripts: format_sft.py (2,012 pairs from the corpus plus 12 hand-written canon pairs), train_lora.py (transformers plus peft, LoRA r=8 alpha=16 on q_proj and v_proj), eval.py (held-out Q and A from eval docs, keyword-recall proxy metric), merge_and_export.py (merge adapter into base, save for GGUF conversion).

Smoke run, 2026-11-20, this VM (CPU, 1.5 cores, 6 GB RAM)

  • Model loaded: Qwen/Qwen2.5-0.5B, from the Hugging Face Hub, unauthenticated download.
  • Trainable parameters: 540,672 of 494,573,440 (0.109 percent). The count matches the hand calculation exactly (24 layers, r=8, q_proj plus v_proj).
  • Steps: 3, on 16 examples, sequence length 128. Runtime 85.3 seconds, about 28.5 seconds per step.
  • Loss: 5.296, then 4.710, then 4.735. Train loss 4.914. Loss moved, but 3 steps on 16 examples teaches nothing. That is the point of a smoke run: it proves the pipeline executes end to end, not that the model learned anything.
  • Adapter saved to runs/smoke. Receipt: runs/smoke/train_receipt.json.

This is a smoke run, not a training run. Do not read learning into it. The real run is 2 epochs over 2,012 pairs on the Mac, per the run-book.

6. The eval harness: base versus adapter

eval.py generates answers from held-out eval docs and scores keyword recall against the source text. It runs in two modes: base-only and with an adapter. The comparison is the proof that the adapter learned from the corpus instead of the base model's memory.

  • Base model (Qwen2.5-0.5B, no adapter), 10 held-out questions: mean keyword recall 0.056 (5.6%)
  • Smoke adapter (3 steps, 16 examples), same 10 questions: mean keyword recall 0.053 (5.3%)

The smoke adapter is expected to score near the base model. Three steps cannot teach a model. The harness exists so the real Mac run can be scored honestly: if the adapter score is not clearly above the base score after 2 epochs, the adapter did not learn and the run-book says to check the training loss first.

7. Neuruh Core v2 Modelfile

An Ollama Modelfile encoding the organism and canon as the system prompt, built on the v1.0 tutorial, not duplicating it. v1 taught editing one SYSTEM block and rebuilding neurah/v1.0; its base model was UNKNOWN and no build was ever verified. v2 names the base (Qwen2.5-0.5B plus the LoRA adapter, merged and quantized to GGUF) and carries real canon content. Same three-part SYSTEM anatomy as v1:

  • OPERATING DOCTRINE: Neuruh is sovereign AI execution infrastructure, not a chatbot. Answer from evidence, say UNKNOWN when you do not know, state follows the CONCEPT to COMMERCIAL ladder, important actions leave receipts, the loop is mission to action to result to receipt to verification to state update to next mission.
  • TRIGGER LEXICON: SAL (a signal becomes a lead only when evidence, recipe, and rank agree), PMLA (a claim needs provenance, measurement, lineage, and authority), RECEIPT (a consequential claim carries its receipt or is marked UNVERIFIED), D-LINE (lead with one line stating what the deliverable does now).
  • OUTPUT POLICY: blunt, direct, execution-first. No emojis, no fluff, no apologies, no hedging. Checklists, command lines, file paths, expected outputs. Copy-paste ready code, no placeholders.

8. The Mac run-book (condensed)

Full run-book: RUNBOOK.md in the program folder, also published with this page. The short version, on the M1 Mac with 8 GB RAM:

# 1. Install
brew install ollama python@3.12 git
python3.12 -m venv ~/neuruh-slm-venv
source ~/neuruh-slm-venv/bin/activate
pip install torch transformers peft accelerate

# 2. Get the program folder (zip it from the build machine, same as the vault)
# 3. Build SFT data
python3 format_sft.py --corpus corpus/corpus_docs.jsonl --out sft_train.jsonl

# 4. Train (the real run: 2 epochs, 2,012 pairs, about 1-3 hours on an M1)
python3 train_lora.py --sft sft_train.jsonl --out runs/v1 --epochs 2 --max-len 512

# 5. Evaluate adapter against base
python3 eval.py --base Qwen/Qwen2.5-0.5B --adapter runs/v1 --limit 20 --out eval_adapter.json
python3 eval.py --base Qwen/Qwen2.5-0.5B --base-only --limit 20 --out eval_base.json

# 6. Merge, quantize, run in Ollama
python3 merge_and_export.py --base Qwen/Qwen2.5-0.5B --adapter runs/v1 --out merged/neuruh-v2
# llama.cpp: convert to GGUF, quantize Q4_K_M, then:
ollama create neuruh/v2.0 -f Modelfile
ollama run neuruh/v2.0

# 7. Publish (only after it runs correctly in Ollama)
huggingface-cli repo create NeuruhAI/neuruh-core-v2 --type model
huggingface-cli upload NeuruhAI/neuruh-core-v2 runs/v1 ./adapter
huggingface-cli upload NeuruhAI/neuruh-core-v2 ./neuruh-v2-q4_k_m.gguf .

The corpus is not published to a public URL. It contains the full text of internal vault notes, and publishing it is Jeramie's call, not a default. The program folder travels to the Mac the same way the vault does.

9. Honest limits

  • No trained model exists. No weights exist. Nothing has been published to Hugging Face or GitHub as weights.
  • Full pretraining is impossible on $0 compute. The corpus is 16M tokens; pretraining needs billions.
  • Full fine-tuning of any model does not fit 8 GB of RAM. LoRA is the method, not a preference.
  • The 3B model (Bonsai's choice) does not fit LoRA training on 8 GB. The 7B model fits nothing on 8 GB.
  • The smoke run proves the pipeline executes. It proves nothing about learning.
  • The RAG sidecar is retrieval, not a language model. It quotes the corpus; it does not reason about it.
  • The eval metric is keyword recall, a proxy. It measures whether the answer mentions the right terms, not whether the answer is correct.
  • Open-source publication happens after weights exist on the Mac and pass the Ollama check. Not before.
