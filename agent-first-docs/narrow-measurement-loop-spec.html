Narrow measurement loop, Jeramie, 2026-11-15 06:47 EST

Instruction: "Narrow first, resolve the measurement loop, then broaden." This is the concrete implementation plan for Layer 1 (real observation) and Layer 2 (pre-registered forecasts with Brier scoring) of the six-layer upgrade spec. It is the first working piece of Retardio (system name when complete, per Jeramie 2026-11-15). Strengthen, do not remove: additive only, it replaces nothing.

Principle

The highest-leverage starting point is a single public data source with clear, observable outcomes that can be scored later. Everything else (authority headers, topology, communication, weight updates) depends on having real observations and forecasts that can be checked.

Chosen narrow domain

Public county property records + related entity filings, focused on a small set of well-documented patterns that appear in published fraud, money-laundering, and scam typology reports (all-cash LLC purchases, rapid flips with large unexplained jumps, newly formed entities with no clear activity, clusters of properties controlled by related entities).

This is fully public in most U.S. counties (assessor, recorder, secretary of state). Outcomes can later be coded from court dockets, news, enforcement actions, or subsequent public filings. It stays at the level of transactions and entities, not private individuals scored as "corrupt."

No other data sources are added until this loop produces calibrated forecasts on held-out historical data.

Layer 1: Observation schema (minimal, typed, receipted)

Every observation is a structured record with provenance. Nothing enters the system without a hash.

{
  "observation_id": "sha256 of canonical payload",
  "source": "county_recorder | secretary_of_state | court_docket",
  "source_locator": "county + instrument_number or filing_id + retrieval_timestamp",
  "retrieved_at": "ISO-8601",
  "raw_hash": "sha256 of exact bytes retrieved",
  "entity_type": "deed | llc_filing | ucc | lis_pendens | judgment",
  "payload": {
    "instrument_date": "...",
    "grantor": "...",
    "grantee": "...",
    "consideration": "number_or_null",
    "property_id": "parcel or address hash",
    "entity_name": "...",
    "formation_date": "...",
    "related_entities": ["..."]
  },
  "schema_version": "1.0"
}

Rules:

  • Canonicalize the payload before hashing (sorted keys, normalized strings).
  • Store the raw bytes or a pointer to them so the hash can be recomputed by an independent party.
  • Append-only log. No updates; corrections are new observations that reference the prior ID.
  • Retrieval method and any API parameters are included in the source_locator so the observation can be reproduced.
  • Start with one county that publishes bulk or API access and has historical data going back at least 5-7 years. Ingest only the fields above. Ignore everything else.

Layer 2: Concrete forecast + Brier loop

Define a small number of pre-registered forecasts. Each forecast is emitted before any outcome is known and is stored with its own receipt.

Example forecasts (only these at first):

  • Rapid-flip typology match. Probability that a deed will be followed, within 180 days, by a subsequent deed on the same parcel with consideration >= 1.5x the prior consideration, and the grantee is an entity formed within the prior 12 months. Forecast issued at the time the first deed is observed.
  • Entity-cluster signal. Probability that a newly observed LLC will appear as grantee on >= 3 distinct parcels within 365 days. Forecast issued at LLC formation or first appearance.
  • All-cash + new-entity signal. Probability that an all-cash (or nominal consideration) purchase by an entity formed < 90 days earlier will later appear in a public enforcement action, civil suit, or published typology report within 24 months.

Each forecast record:

{
  "forecast_id": "...",
  "observation_ids": ["..."],
  "forecast_type": "rapid_flip | entity_cluster | all_cash_new_entity",
  "probability": "0.0-1.0",
  "issued_at": "ISO-8601",
  "model_version": "baseline_v1",
  "features_used": ["consideration_ratio", "entity_age_days", "prior_deed_count"],
  "receipt": "sha256 of the forecast record"
}

Outcome coding (later). When the window closes or a public record resolves the question, an outcome record is written:

{
  "outcome_id": "...",
  "forecast_id": "...",
  "resolved_at": "...",
  "outcome": "0 or 1",
  "evidence_observation_ids": ["..."],
  "coder": "human | rule",
  "receipt": "..."
}

Brier score. For a set of resolved forecasts: Brier = (1/N) * sum((p_i - o_i)^2). Lower is better. Track overall Brier, Brier by forecast type, and Brier over time. Publish the numbers. A model or weight update is retained only if it improves Brier on a subsequent or held-out set of forecasts (not the set used to propose the change).

Initial model can be a simple logistic regression or even a transparent scoring rule on the features. The point is not sophistication; it is that every probability is issued in advance and later scored.

Narrow operating loop (resolve this before broadening)

  • Ingest observations from one county into the append-only log.
  • On each new relevant observation, emit the applicable forecasts with receipts.
  • Wait for natural resolution windows or public outcomes.
  • Code outcomes and compute Brier.
  • Only after a stable Brier is demonstrated on historical back-test + forward test, allow a human-reviewed proposal to adjust the scoring rule.
  • Re-test the adjusted rule on new data. Keep it only if Brier improves.
  • All steps produce receipts. An independent party can re-compute hashes and Brier from the exported log.

Success criteria for this narrow slice (examples):

  • >= 200 resolved forecasts.
  • Brier meaningfully better than a constant baseline (e.g., always predicting the base rate).
  • Receipt chain verifies end-to-end.
  • False-positive rate on a pre-specified threshold is acceptable to a human reviewer.

Broaden only after the above is resolved

Once the observation schema, forecast issuance, outcome coding, and Brier gate are working on one county and one set of typologies:

  • Add a second county (same schema).
  • Add one additional public source (e.g., state corporate registry bulk data or a published scam-wallet list with on-chain observations).
  • Add one new forecast type that re-uses the same machinery.
  • Introduce a minimal authority header on any alert or export (who authorized the threshold, expiry, scope).
  • Only then consider topology or multi-module coordination.
  • Each broadening step must re-demonstrate calibration on the new data before the next step is allowed.
