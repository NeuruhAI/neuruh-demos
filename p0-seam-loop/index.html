P0 Seam Reference Loop

Receipt watcher → Sentinel invocation → result ingest → custody → promotion. Browser demo of the Node module p0-seam.js. The same file powers both: the Node tests (node test.js, 33 checks) and this page.

What this is: a working reference implementation of the missing automatic handoff in the Neuruh organism: a receipt watcher observes a sealed receipt ledger, Sentinel (CRUCIBLE gate) scores each world, outcomes are ingested back onto the same hash-chained ledger, and only a SHIP-CANDIDATE with a real external signal promotes.

What this is not: the production loop. The production loop lives on Jeramie Hicks' Mac (launchd ticks, the always-running Switchboard, the loopback Sentinel organ at 127.0.0.1:18731). Nothing on this page touches it, reads from it, or claims to be it.

Receipt standard: receipt v1.0, SHA-256 hash chain, first prev hash is the literal string GENESIS, canonical JSON with the hash field stripped before hashing. Source: the Land Intelligence Report store (buildReceipt). The N-Cell adapter demo uses FNV-1a 32-bit hashing; that is demo-only and is not used here. Every hash on this page is SHA-256.

1. The formulas

  • CRUCIBLE gate score = max(0, emergence_raw - objection_penalty) x multiplier
  • Multiplier ladder: revenue / signed contract 1.00, paid pilot 0.50, one real lead 0.30, nothing 0.15
  • Verdicts: KILL below 20, ITERATE 20-49, SHIP-CANDIDATE at or above 50 only with a real external signal (50+ without a signal downgrades to ITERATE)
  • Strikes: a KILL adds one strike. The first KILL does not move the file. kill_move fires only at strike 3.
  • Doctrine eta = (I_q x I_r x I_v) / (1 + E_wasted + C_violations), bounded 0-100. Seed requires eta ≥ 70 AND feedback accuracy ≥ 0.6.
  • Promotion gate: only SHIP-CANDIDATE with a real external signal promotes. SHIP-CANDIDATE without a signal, ITERATE, and KILL are all refused.

2. Run the loop

Seeds a two-receipt GENESIS ledger, then runs three worlds through Sentinel, ingests each outcome as a new chained receipt, and checks promotion.

4. The ledger after a run

Every outcome receipt is chained onto the same ledger: its prev hash is the previous receipt hash, and the whole chain re-verifies after ingest.
