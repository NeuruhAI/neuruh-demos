2. What the Opus App is

Per the Master Plan (00), the Opus App is a "Napkin to Production" engine: a cohesive, high-fidelity SaaS dashboard that takes a user from "Idea" to "Production". The build role named in the plan is Senior Frontend Architect and Product Engineer. The plan names three views, a simulated backend, a fixed visual system, and a security layer, and it orders the work in five phases (Section 4 and Figure 1).

The product concept, in the plan's own terms:

  • Idea to production: one dashboard carries a user from an idea to a production deployment.
  • Three views: Customer Usage (resource consumption), User Metrics (growth and churn), Pay Plans (subscription tiers).
  • Simulated backend: endpoints for usage, financials, and pricing tiers, built with a "Math + AI" hybrid approach, with user inputs persisting globally.
  • Fixed aesthetic: "Soft Bento Glass", defined in 01, applied to every page, with an explicit constraint of no dark mode.
  • Security layer: rate-limiting middleware and input validation with Zod, added as a new requirement in the plan.

What the Opus App is not, on current evidence: it is not a live product, not a deployed app, not a revenue system, and not DeedSonar or any other Neuruh product. No source links the Opus App to a customer, a deploy URL, or a production database.

4. 00 Master Plan

00_Master_Plan.md DESIGNED

Source: Google Doc, Drive file id 1QeAq5-u3eu5iD_9MAaZCLkOGvfA7mvpqSDTLudAw1z8. Modified 2026-01-22T22:20:52Z. Recorded size 4,090. Read from Google Docs, 2,242 characters extracted. Drive link. Local item record: ~/workspace/drive-build/items/s11-00-master-plan-md.md.

What it is

The master execution plan for the whole build. Title in the source: Master Execution Plan, "Napkin to Production" Engine. It sets the role (Senior Frontend Architect and Product Engineer), the objective (a cohesive, high-fidelity SaaS dashboard from Idea to Production), and one strict constraint: no dark mode, the "Soft Bento Glass" aesthetic from 01 applies to every page.

What it specifies

Five phases, in order, each naming its reference file:

  1. Phase 1, The Design System (Visual Foundation). Reference: 01_Design_System.md. Update tailwind.config.js immediately with the stone and glass tokens. Set the body background to stone-50. Install Inter (UI) and JetBrains Mono (Data). Create the <GlassCard /> component to match the "Physics" in the spec exactly (borders, blur, shadow).
  2. Phase 2, The Logic Core (Backend and Data). Reference: 02_Backend_Logic.md. Create the simulated backend endpoints using the "Math + AI" hybrid approach: /api/metrics/usage (usage logic), /api/metrics/financials (MRR and churn logic), /api/pricing/tiers (feature gates). User inputs persist globally. New security layer: rate-limiting middleware (see Phase 5) and input validation using Zod.
  3. Phase 3, The Dashboard Views (Frontend). Reference: 04_View_Definitions.md. Usage Dashboard ("Resource Consumption" view with Free Tier Caps visible), User Metrics ("Growth and Churn" view), Pay Plans ("Subscription Tier" view). New export actions: "Download CSV" buttons on all data tables.
  4. Phase 4, Data Visualization (Charts). Reference: 03_Component_Specs.md. Chart overrides: forbidden from using default Recharts colors. All charts use stroke-stone-800 for lines and fill-stone-200 for areas. New locked states: the "Glass Lock" overlay for non-paying users.
  5. Phase 5, Security and Production Hardening (NEW). Reference: 02_Backend_Logic.md. Rate limiting: Free Tier 100 requests per hour, Pro Tier 10,000 requests per hour, return 429 Too Many Requests with a custom JSON error. Data export: implement /api/export/csv, which takes a dataset ID and returns a formatted CSV stream.

The plan closes with an action: start with Phase 1, and confirm when the Tailwind config is complete. No completion confirmation is on record anywhere in the sources for this doc.

State

DESIGNED The plan is a design document. The phases describe work to do. Phase 1 through 5 completion is not evidenced by any source. The simulation demo (Section 10) implements the plan's views and limits in a browser, which is a simulation of the plan, not execution of it.

Source: Google Doc, Drive file id 1asyk7LrmR8qULdypqLMMEuHvvlT2fO8etRbLB0XYTn4. Modified 2026-01-20T13:39:00Z. Recorded size 2,623. Read from Google Docs, 1,330 characters extracted. Drive link. Local item record: ~/workspace/drive-build/items/s11-01-design-system-md.md.

What it is

The visual system for the whole app, named "Soft Bento Glass". Directive: a neutral, tactile, high-production aesthetic. Reference: "Apple Park Visitor Center", natural light, stone, frosted glass.

What it specifies

  • Color palette (Tailwind). Rule: no pure black (#000), no cool or blue grays, use Warm Stone. Stone 50 #FAFAF9 (canvas background), 100 #F5F5F4 (sidebar and surface), 200 #E7E5E4 (borders), 400 #A8A29E (subtitles), 600 #57534E (body text), 800 #292524 (headings), 900 #1C1917 (high contrast accents). Glass base rgba(255, 255, 255, 0.4) (card background), border rgba(255, 255, 255, 0.6) (card rim), active rgba(255, 255, 255, 0.7) (hover state).
  • The "Glass Card" Physics. Every container in the app must use this structure. Classes: bg-white/40 backdrop-blur-xl border border-white/50 shadow-sm rounded-3xl. Hover: hover:scale-[1.01] hover:bg-white/60 hover:shadow-md transition-all duration-300 ease-out.
  • Typography. Headings: Inter (Bold, Tracking Tight -.02em), stone-800. Data: JetBrains Mono (Medium), stone-600. Body: Inter (Medium, Leading Relaxed), stone-600.
  • Layout: The Bento Grid. Standard: grid grid-cols-1 md:grid-cols-4 gap-6. Hero widgets: col-span-2 row-span-2. Standard widgets: col-span-1 row-span-1.

6. 02 Backend Logic

02_Backend_Logic.md DESIGNED

Source: Google Doc, Drive file id 11bHqB78H1iu3C15TjDwADfULFRnxKPQWW-dlYBiqIlw. Modified 2026-01-20T13:39:11Z. Recorded size 3,390. Read from Google Docs, 1,689 characters extracted. Drive link. Local item record: ~/workspace/drive-build/items/s11-02-backend-logic-md.md.

What it is

Backend logic and data simulation. Directive: real logic only, no "Lorem Ipsum", include security protocols. It defines three engines plus a middleware and an export engine. All endpoints are simulated; no real backend exists on any record.

What it specifies

  • 1. User Metrics Engine (The Growth Dashboard), endpoint /api/metrics/growth. Inputs: InitialUsers (example 100), GrowthRate (example 1.15). Algorithm: loop 12 times (12 months). NewUsers = PreviousMonth times GrowthRate. ChurnedUsers = PreviousMonth times 0.05 (5 percent churn). NetUsers = NewUsers minus ChurnedUsers. Output JSON fields: mrr, churn_rate, active_users, history (month, users, churn per month). The sample output in the source carries example values for churn rate and active users; the sample MRR value is a cash figure in a spec example and is withheld here per the standing rule against restating cash figures. All of these are spec example values, not measured figures.
  • 2. Customer Usage Engine (Free Tier Logic), endpoint /api/metrics/usage. Security check: check the Authorization header, return 401 if missing. Algorithm: generate random "spikes" to mimic real-world usage. Free Tier Logic: if user.plan is "free", cap storage.used at 5GB. Output JSON example: api_usage total "1.2M", status "Healthy", limit "2M"; storage used "45GB", total "100GB", percent 45; is_throttled false. These are example values in the spec, not live measurements.
  • 3. Security Protocols (Middleware), rateLimit.js. Sliding window counter. Free user: max 5 requests per minute. Pro user: max 100 requests per minute. Violation response JSON: error "RateLimitExceeded", message "You have hit the Free Tier limit. Upgrade to Pro for unlimited access.", retry_after 45.
  • 4. Export Engine, endpoint /api/export/data. Inputs: type "csv", dataset "financials". Logic: convert the JSON dataset from Endpoint 1 into a CSV string. Headers: Content-Type text/csv, Content-Disposition attachment with filename "report.csv". Note in the source: this must happen server-side to simulate a real production export.

State

DESIGNED The logic is specified, including formulas, limits, and error payloads. No server implements it. The simulation demo reproduces the rate-limit behavior and CSV export in the browser, which is a simulation of this spec, not a backend.

Source: Google Doc, Drive file id 1W77VBRLd6dIot9YmauvOU1WxVw2QAz2jtC1kpA67XlY. Modified 2026-01-20T13:39:16Z. Recorded size 3,248. Read from Google Docs, 1,489 characters extracted. Drive link. Local item record: ~/workspace/drive-build/items/s11-03-component-specs-md.md.

What it is

Component specifications and chart styling: four components that carry the visual system into interactive behavior.

What it specifies

  • 1. The "Clean" Chart (Recharts). Directive: override all default colors. Charts must look like technical drawings on glass. Area chart spec: grid <CartesianGrid strokeDasharray="3 3" vertical={false} stroke="#E7E5E4" /> (horizontal lines only, Stone-200). Tooltip: custom component, bg-white/80 backdrop-blur-md border border-white/60 shadow-lg rounded-lg, JetBrains Mono, text-xs. The line: <Area type="monotone" stroke="#292524" strokeWidth={2} fill="url(#colorGradient)" />, stroke stone-800 (almost black). The fill: gradient from stone-300 (top) to transparent (bottom).
  • 2. The "Glass Lock" Overlay (NEW). Usage: when a Free user tries to access Pro features. Style: container absolute positioning over the card (inset-0). Material: bg-white/10 backdrop-blur-sm (subtle blur of the content below). Icon: a centered padlock icon (Lucide-React) in stone-400. Call to action: a small "Upgrade" button (scale-75) below the lock.
  • 3. The "Export" Action (NEW). Usage: top right of dashboard tables. Style: button "Ghost" variant. Icon: Download icon (w-4 h-4). Text: "CSV" (text-xs font-mono). Interaction: on click, show a small "Preparing..." spinner, then trigger browser download.
  • 4. The "Magnetic" Button. Interaction: uses framer-motion. On hover, the button translates x/y by 20 percent of the mouse position (magnetic pull). Style: bg-stone-900 text-stone-50 rounded-full px-6 py-3 font-medium shadow-lg hover:shadow-stone-900/20.

State

DESIGNED All four components are specified. They exist as running code only inside the browser simulation demo, which implements the Glass Lock, the CSV export action, and the magnetic Subscribe button per this spec.
