## 1. The idea in one page

Two systems, one principle: **lock what must stay constant, vary only what must change, and never let the AI decide the parts that carry truth.**

**Half one is prompt-level: the Token-Swap Template System.** A prompt is split into a fixed Master Foundation (visual DNA: technical specs, core subject, environment, style directives) and variable Swap Tokens (placeholders such as `<ANGLE_TOKEN>`). You change one token, everything else stays identical, and a series of images looks like it was shot by the same photographer on the same day. This solves "prompt roulette": small wording changes no longer derail the aesthetic.

**Half two is pipeline-level: programmatic compositing.** Instead of asking one flat image generator for a finished, baked JPEG, the system treats AI strictly as an asset creator. An Architect Agent parses intent into a structured JSON payload (the Davinci protocol). An Asset Generation Agent produces backgrounds in ComfyUI with ControlNet enforcing layout boundaries and reserved negative space. An Assembly Agent pushes the assets, user-uploaded photos, and HTML/CSS typography into an editable Fabric.js or Polotno canvas. Pillow handles the export math (300 DPI CMYK for print, 72/96 DPI RGB for digital). Text is never generated by the image model, so it is never misspelled.

**The two halves connect.** A token-swap master template is the prompt that the Asset Generation Agent runs. A Davinci JSON payload is the envelope that carries the template, the token choices, the user uploads, and the typography into the canvas. The Remodel Vision Pro agent and the AI Resale Listing Engine are the same pattern applied to two verticals: remodel visualization (photo in, prompt out) and resale listings (photo in, listing out).

**The rule that governs both halves:** AI generates, Jeramie authorizes, the system executes. Nothing in this document posts, sends, spends, or publishes on its own.

## 2. Anatomy of a token-swap template

Think of it like a movie production. The set, lighting, and camera equipment stay locked. Only specific directions change.

### 2.1 The Master Foundation (visual DNA)

The non-negotiable elements. Everything that defines the look, feel, and technical execution:

- **Technical specs:** camera settings, rendering quality, lighting conditions
- **Core subject:** the main focus (a luxury estate, a house, a shield, an altar)
- **Environment:** landscape, architecture, materials, colors
- **Style directives:** what to emphasize, what to avoid

The foundation acts as a **World Bible**. You meticulously define the permanent world so the AI does not have to guess. An infinity pool in one shot is the exact same infinity pool in the next because you gave the model the blueprints: grand colonial massing, standing-seam metal roof, 70 percent mature hardwood forest, gravel and flagstone paths connecting all nodes.

### 2.2 The Swap Tokens

Variable elements, marked with tags such as `<ANGLE_TOKEN>`. Swap one token to change the angle, focus, season, mood, or emphasis without breaking visual continuity. Token families used across the sources in this document:

- `<ANGLE_TOKEN>` (camera position, the most important token)
- `<SEASON_TOKEN>`, `<MOOD_TOKEN>`, `<TIME_TOKEN>` + `<LIGHTING_TOKEN>` (conditional pairs)
- `<ENHANCE_TOKEN>` (micro-modifier, a director's note)
- `<HOUSE_TYPE_TOKEN>`, `<STYLE_TOKEN>`, `<LOCATION_TOKEN>`, `<ERA_TOKEN>`, `<ARCHITECTURE_DETAILS_TOKEN>`, `<MATERIAL_TOKEN>`, `<FEATURE_TOKEN>`, `<LANDSCAPE_TOKEN>`, `<CONTEXT_TOKEN>`, `<WEATHER_TOKEN>`, `<CAMERA_TOKEN>`, `<ASPECT_RATIO_TOKEN>`, `<COLOR_PALETTE_TOKEN>`, `<POSTPROCESS_TOKEN>`

### 2.3 The five parts of a complete template

1. **The Master Style (the foundation line).** The non-negotiable aesthetic contract. Quality, lighting, overall feel. Never changes.
2. **The World Bible (the unchanging details).** SUBJECT, MAIN RESIDENCE, LANDSCAPE, WATER SYSTEM, OUTBUILDINGS, SETTING/VIEWS. The overwhelming concrete detail that anchors the model.
3. **The Swap Tokens.** The camera moves; the world stays.
4. **The Technical Direction (the camera).** Aperture, shutter, ISO, color depth, optical imperfections. Section 6 explains what each setting actually does and where the sources overstate the physics.
5. **The Bouncer (the negative prompt).** Everything you do not want. Quality control against common AI artifacts.

### 2.4 Why it works

- **Visual consistency.** Every image shares the same technical foundation, lighting, and aesthetic DNA.
- **Efficient iteration.** Swap one token instead of rewriting the prompt.
- **Quality control.** Negative prompts and technical specs are baked into every generation.
- **Scalability.** Dozens of angles and focuses without losing the core aesthetic.

### 2.5 How to build your own

1. Define your Master DNA (technical quality, lighting, core subject, style boundaries).
2. Identify your variables (angles, focus areas, seasons, architectural emphasis, mood).
3. Create your token library (drop-in options per variable).
4. Test and refine (generate a series with different combinations, tune the master based on what works).

### 3.4 How to use it

1. Copy the entire template above.
2. Replace `<ANGLE_TOKEN>` with any of the P1-P7 options.
3. Generate your image.
4. Want a different angle? Swap in a different P option. Same lighting, same quality, same aesthetic DNA, just different perspectives.

### 3.5 The breakdown (why each part matters)

**The Master Style.** The first line is the non-negotiable aesthetic contract. By defining physically based materials and global illumination, you tell the AI to simulate how light behaves in the real world, which is the key to photorealism. This part never changes.

**The World Bible.** Meticulous detail anchors the model. You are not saying "a modern house"; you are describing grand colonial massing, a standing-seam metal roof, specific tree species, and the path system connecting the buildings. The infinity pool in one shot is the exact same infinity pool in the next.

**The `<ANGLE_TOKEN>`.** The virtual camera. The entire world bible remains fixed; you tell the AI where to stand. You can build a whole shot list the way a film director would: P4 Workshop Interior, P5 Zipline Tower Detail, P6 Guest Cottage Sunset View.

**The ENHANCE token.** A micro-modifier or director's note. As written, `<"Professional landscape architecture showcase" Atmospheric perspective haze>` tells the AI to pay extra attention to plantings, lighting, and stonework, adding haze for depth. Swap it to `<"Focus on the smart-home technology" highlighting the glow of recessed LEDs and control panels>` for a tech-focused image, or `<"Emphasize the autumnal colors" making the maple and sweetgum foliage the star of the shot>`.

**The Technical Direction.** Camera settings linked to real-world photography: aperture, shutter speed, ISO. These push the result away from generic AI art and toward professional photography. Section 6 gives the honest version of what each setting does.

**The Bouncer.** The negative prompt is quality control: a list of everything you do not want, cleaning up common AI mistakes and preventing weird artifacts.

### 3.6 Build your own from this pattern

1. Choose your world (swap the luxury estate for anything: a cyberpunk megalopolis, a tranquil elven village, a gritty WWII battlefield).
2. Build your bible (key buildings, foliage, materials; more detail means more consistency).
3. Define your tokens (`<ANGLE_TOKEN>` is essential; consider `<OBJECT_TOKEN>` for vehicles in a driveway or `<TIME_OF_DAY_TOKEN>` for golden hour, midday, twilight).
4. Set your style (master aesthetic, camera settings, negative prompts).
5. Shoot (start swapping tokens and generate a consistent series).

### 4.5 Best practices and advanced deployment

- **Batch generation.** Feed tokens and fields from a spreadsheet or database. Auto-generate hundreds of variations for rapid prototyping, agent demos, or client options.
- **Agent integration.** Deploy as prompt-chains inside n8n, Make.com, Zapier, or the Neuruh stack. Users pick from dropdowns (token banks) and execute on demand.
- **A/B/C testing.** Test different angle, style, and season tokens for conversion rates in listings or ads. Quantify what images pull the best results.
- **Condition and repair visualization.** Swap tokens to show "as-is," "renovated," "distressed," "upgraded." Suited to real estate, insurance, or investor platforms.
- **Contextual opportunity images.** Use context tokens to generate scenes for specific use cases: "under contract," "new listing," "open house," "estate sale."
- **API ready.** Each token can be programmatically inserted or randomized for enterprise-level scale.

## 6. The technical direction anchor (the TECH block) and what it really does

This is the part Jeramie flagged in his 2026-11-17 message as the lock-in. The sources treat these settings as a "technical anchor" inside the Master Foundation. They work. But not for the reason the sources claim. This section gives the honest version.

### 6.1 The locked settings

From the estate template (Section 3) and the house system (Section 4):

- **Lens:** hybrid cinelens, a blend of 24 mm + 50 mm
- **Aperture:** f/8
- **ISO:** 100
- **Shutter:** 1/320 s
- **Color depth:** 12-bit RAW (house templates) / 16-bit per channel (Templar stack, Section 8)
- **Optical imperfections:** subtle chromatic aberration on glass, lifelike foliage via subsurface scattering (SSS)
- **Lighting physics:** physically based materials, global illumination, volumetric sun rays, atmospherics (dust/mist)

### 6.2 What each setting actually signals to the model

- **f/8** signals deep depth of field and architectural sharpness. Real architectural photographers shoot f/8 to f/11 so the whole building is in focus. The model has seen millions of f/8 architectural shots, so the token pulls that look.
- **24 mm + 50 mm blend** signals a wide-but-not-distorted architectural frame. 24 mm is the classic wide architectural lens; 50 mm is the natural human-eye lens. The blend asks for wide coverage without fisheye distortion.
- **ISO 100** signals clean, noise-free, bright-daylight capture.
- **1/320 s** signals a frozen, sharp, handheld-or-tripod still with no motion blur.
- **12-bit / 16-bit RAW** signals rich, workable color with smooth gradients instead of compressed 8-bit banding.
- **Chromatic aberration on glass** signals a real lens, not a render. Deliberate imperfection is what breaks the "too perfect" AI look.
- **Subsurface scattering** signals light passing through translucent material (leaves, skin, marble) instead of bouncing off a flat surface. This is the single biggest realism lever for foliage.
- **Physically based materials (PBR), global illumination, volumetric rays, atmospherics** signal a light simulation rather than a flat illustration. Dust and mist give the air depth, which is what separates a photo from a 3D render.

### 6.3 The honesty notes (read before you trust the numbers)

1. **The hybrid cinelens is not a real lens.** No camera has a 24 mm + 50 mm blend lens. It works as a style anchor, a compressed instruction that tells the model "wide architectural coverage, natural perspective, no distortion." Treat it as a prompt token, not a piece of equipment.
2. **The exposure math is not real-world.** f/8, ISO 100, 1/320 s at golden hour would underexpose a real photograph; golden hour needs a slower shutter or higher ISO or a wider aperture. The numbers are a signal ("bright, sharp, clean"), not physics. Do not defend them as exposure science.
3. **12-bit vs 16-bit is inconsistent across the sources.** The house TECH block says 12-bit RAW; the Templar tech specs say 16-bit per channel. Both are "more color depth than 8-bit." Pick one per template and stay consistent. 16-bit is the stronger claim; 12-bit is the more common camera-RAW claim.
4. **"8K" is an upscale target, not native output.** Native generation is 1K-2K on most engines (4K on Nano Banana and FLUX 3, Section 14). "8K" in a prompt tells the model to render fine detail as if for a large print; the actual pixels come from upscaling (Topaz, ESRGAN, Magnific) after generation.
5. **The settings are a contract with the model, not with a camera.** Their value is consistency: the same TECH block on every prompt in a series is what keeps the series looking like one shoot.

### 6.4 The TECH block, recommended canonical form

Use this as the default TECH block for new templates. It keeps the sources' settings and drops nothing, but it is labeled honestly in the doc:

```
TECH: f/8 hybrid cinelens (24 mm + 50 mm blend), ISO 100, 1/320 s, 16-bit color depth, subtle chromatic aberration on glass, lifelike foliage via subsurface scattering, physically based materials, global illumination, volumetric sun rays, atmospherics (dust/mist)
```

Note the change: 16-bit replaces 12-bit as the canonical depth, because the Templar stack (the most technically detailed source) uses 16-bit and it is the stronger, still-plausible claim. If a specific engine responds better to 12-bit RAW, override per engine in the adapter (Section 14).

## 7. Negative prompts, ENHANCE, conditional tokens, micro-modifiers

### 7.1 The negative prompt (the Bouncer)

The standard NEGATIVE block from the estate template:

```
NEGATIVE: cartoonish, over-saturated HDR, tilt-shift gimmicks, fisheye, blown highlights, muddy shadows, AI glitches, warped geometry, watermark, text artifacts
```

The Templar stack adds its own negative protocol (Section 8.6). The purpose is the same: quality control against the most common AI failure modes. Warped geometry and text artifacts are the two that matter most; cartoonish and over-saturated HDR are the two that most often creep in when a prompt is under-specified.

**Engine reality, 2026 (Section 14):** negative prompts are engine-specific now. Midjourney has only `--no`. GPT Image and Nano Banana do not take negative prompts at all; exclusions must be phrased positively ("matte finish, no gloss") or handled by editing after generation. The old stacks paste NEGATIVE blocks everywhere. When adapting a template to GPT Image or Nano Banana, convert each negative into a positive instruction and drop the NEGATIVE block.

### 7.2 The ENHANCE token (micro-modifier)

A director's note that biases the render toward specific details without altering the core structure. From the estate template:

- Default: `<"Professional landscape architecture showcase" Atmospheric perspective haze>` (focus on plantings, lighting, stonework; haze for depth)
- Tech focus: `<"Focus on the smart-home technology" highlighting the glow of recessed LEDs and control panels>`
- Seasonal focus: `<"Emphasize the autumnal colors" making the maple and sweetgum foliage the star of the shot>`

Rule: one ENHANCE token per prompt. Two competing emphases cancel each other out and the model picks one at random.

### 7.3 Conditional tokens

Paired tokens that work together. The sources' example: link a `<TIME_TOKEN>` ("Dusk") with a specific `<LIGHTING_TOKEN>` ("Warm backlighting with deep blue sky gradient"). The pairing matters because time and lighting are physically coupled; a mismatched pair (midday + warm backlighting) produces the muddy, inconsistent light the negative prompt is trying to prevent.

Conditional pairs used across the sources:

- TIME + LIGHTING (dusk / warm backlighting; noon / hard shadows; midnight / window glow)
- SEASON + LANDSCAPE (autumn / maple reds; winter / evergreen contrast; spring / dogwood blossoms)
- WEATHER + LIGHTING (rain / wet pavement reflections; fog / diffused halos; clear sky / crisp shadows)

### 7.4 Micro-modifiers (the [A] slot)

The estate template's `[A] Modern Tech Emphasis` is a micro-modifier: "Tech-forward minimalism; reveal smart systems (hidden tracks, auto louvers), sleek concrete/cor-ten steel, broad glass planes, clean lines." It sits between the world bible and the ENHANCE token and shifts the whole template's emphasis in one line. Build a small library of [A] slots per template (tech emphasis, heritage emphasis, landscape emphasis, interior emphasis) and swap them the same way you swap angles.

### 7.5 Automation

Once the token logic is defined, it can be automated with agentic workflows (n8n, Section 4.6) to batch-generate hundreds of variations by programmatically swapping tokens from a structured list. The Davinci protocol (Section 11) is the structured form of the same idea: the JSON payload carries the token choices, and the Assembly Agent renders them.

## 11. The agentic architecture: Davinci protocol and programmatic compositing

Source: "Technical Specification: Agentic Architecture for Programmatic Design Compositing." The pipeline half of the system. Flat image generation produces one baked JPEG with garbled text and no editability. Programmatic compositing produces an editable canvas where every layer stays independent.

### 11.1 Flat generation vs programmatic compositing

| | Flat generation | Programmatic compositing |
|---|---|---|
| Output | One baked JPEG | Editable canvas (layers) |
| Text | Generated by the image model, often misspelled | HTML/CSS layer, always correct |
| Layout | Whatever the model decides | Enforced by ControlNet grid + reserved space |
| Editability | None: regenerate the whole image | Swap any layer, resize, retype |
| Export | Whatever the model outputs | Pillow: 300 DPI CMYK print or 72/96 DPI RGB digital |

### 11.2 The stack

| Layer | Tools (from the source) |
|---|---|
| Agentic orchestration | CrewAI or LangChain: agents coordinate, JSON payloads pass between them |
| Image generation and layout control | ComfyUI (node-based Stable Diffusion GUI) + ControlNet: a black-and-white grid forces the AI to generate inside defined boundaries and leave designated space for text |
| Canvas engine | Fabric.js or Polotno: HTML5 canvas, programmatic layers, text boxes, image placeholders, editable in the browser |
| Technical processing and export | Python Pillow: force 300 DPI for print, add bleed margins, convert RGB to CMYK |

### 11.3 Agent roles

- **Intake Agent:** takes the user's request (natural language, uploads, or both) and normalizes it into structured input.
- **Architect Agent:** parses intent into the Davinci JSON payload. Selects fonts and colors by mapping descriptive adjectives to pre-defined design patterns: "edgy, modern flyer" maps to a dark palette and a sleek sans-serif; "professional" maps to high-contrast hex and conservative ratios. Specifies exact font families (Montserrat-Bold for headlines, OpenSans-Regular for subtext) and exact hex codes. Never lets the image model choose typography.
- **Asset Generation Agent:** runs the image generation (ComfyUI + ControlNet) for backgrounds and supporting assets. Prepares user-uploaded photos: background removal, color correction, reserved empty space in the generated background for the upload to sit in.
- **Assembly Agent:** pushes the assets into Fabric.js or Polotno as independent layers, applies the typography as HTML/CSS, and hands the user an editable canvas.

### 11.4 The Davinci tokenization protocol

"Davinci" is the spec's own name for its JSON protocol, not an external standard. The JSON payload is the tokenized protocol that translates creative intent into structured, actionable data. It organizes a project into a nested `layers` object:

- **Layer segmentation:** each element is a separate component. A background layer carries a detailed prompt for a high-end residential neighborhood; a hero_image layer specifies a source file and an action such as "remove_background".
- **Spatial and technical parameters:** global project data (dimensions, aspect ratio) plus specific positions for assets such as logos or headshots ("bottom_right").
- **Typography as data:** a typography object defines exact text content, font family, hex color, and alignment for headlines and subtext. Because text is defined in the payload, it renders as actual HTML/CSS over the AI-generated background. The user can click the text to change a word or tweak sizing before export.
- **Programmatic assembly:** because layers are defined in JSON, the Assembly Agent pushes each asset into the canvas engine as an independent, editable layer.

The full verbatim "Just Sold" Instagram payload is in Appendix B.

### 11.5 User-upload priority pipeline

Prioritizing templates where users upload their own photos transforms the pipeline from a creative hallucinator into a precision compositing engine:

1. **Asset mapping:** the Architect Agent assigns the upload to a layer in the JSON payload (hero_image or branding), with actions such as "remove_background" or "color_correct".
2. **Targeted asset processing:** the Asset Generation Agent prepares the user's specific image (background removal APIs for headshots, color correction) and ensures the AI-generated background leaves a specific empty space for the uploaded photo.
3. **Programmatic assembly:** the Assembly Agent places the processed photo as an independent layer in Fabric.js or Polotno. The user can click, resize, or swap it in the browser.
4. **Professional export:** Pillow forces the whole canvas, including uploads, into 300 DPI CMYK for print or 72 DPI RGB for digital social posts.

This bypasses the core limitation of traditional AI generation, which struggles to render a specific uploaded item accurately inside a generated scene. The photo stays the photo; the AI builds around it.

### 11.6 Why this matters for the token-swap system

The token-swap template (Sections 2-5) is the prompt the Asset Generation Agent runs. The Davinci payload (Section 11.4) is the envelope that carries the template, the token choices, the user uploads, and the typography into the canvas. A token-swap master template plus a Davinci payload plus a Fabric.js canvas is the complete product: consistent images, correct text, editable output, professional export. Either half alone is incomplete: prompts without compositing give you baked JPEGs with garbled text; compositing without token discipline gives you editable layouts with inconsistent imagery.

Source: "AI as a Solution: The Creator Economy" (63 pages, NotebookLM-style compilation of Jeramie's own source documents, briefing dated October 26, 2023). This is the commercial frame for everything in Sections 2-12. The token-swap templates are the product; this section is how the product is packaged, licensed, and sold.

**Honesty note first:** Buildstream, the platform this document describes, is a design and vision document, not a live platform. There is no evidence in the source that Buildstream exists as a running product. Treat everything in this section as a commercial architecture to build toward, not a platform to join. The @CardMasterMike persona quoted throughout is a fictional example, not a real person. The source document repeats itself heavily (the briefing appears twice, the finalized structure appears twice, the same AaaS definition appears in four forms); this section is the deduplicated version.

### 13.1 AaaS: AI as a Solution

"SaaS solved software delivery. AaaS solves human-scale problems, by deploying intelligence as the product."

AaaS delivers done-for-you outcomes powered by autonomous logic, instead of selling access to software tools. The shift:

- **Access vs execution.** SaaS gives you the software. AaaS gives you the solution already running, with logic, agents, memory, and outcomes. "SaaS is about access. AaaS is about execution."
- **Tools vs solutions.** SaaS provides the tools to perform a task. AaaS provides a system or agent that directly addresses the need and delivers a specific outcome.
- **Selling logins vs selling outcomes.** In SaaS you sell logins. In AaaS you sell decision power, agent access, licensed knowledge, self-executing workflows, and systemized solutions. Users select outcomes ("Get leads," "Grade cards," "Audit deals," "Generate revenue") instead of features.
- **Static software vs intelligent assets.** SaaS is a static product with periodic updates. AaaS assets (agents, capsules) embody the creator's logic, operate autonomously, and are remixable and licensable.
- **Beyond simple automation.** AaaS is not chatbots or auto-replies. It is modular agent stacks, adaptive frameworks, real-world deployment flows, and monetizable IP capsules.

**AaaS vs content platforms:** content platforms host passive content and monetize through ads or subscriptions. AaaS platforms host logic-based goods. Every capsule is interactive, remixable, and directly monetizable. Users build upon the work with a remix button instead of passively consuming it. The platform is a rights-based intelligence marketplace, not a feed.

### 13.2 The five-phase timeline (from the source)

- **Phase 1: Foundational concepts.** AaaS defined; SaaS distinction drawn; AaaS as a marketplace of intelligence.
- **Phase 2: Buildstream and its AaaS-native structure.** The platform positioned as the first AaaS-native platform; six layers defined (Section 13.3).
- **Phase 3: Empowering creators, the CreatorOS.** Identity Layer, Live Capsule Feed, Storefront, Agent Zone, Remixable Profile Stack, Vaults, Dashboard, Tiers.
- **Phase 4: Remixability, monetization, Builder Agents.** Capsule types, agent monetization models, Intelligence Products, IP monetization hub.
- **Phase 5: Enhanced vision.** CreatorOS for the agent economy; owning logic and building a legacy; external platform integration; AI-driven amplification; win-based feedback loop; future features (agent-made merch, AI podcast agents, creator capsules as NFTs, "Powered By" badges).

### 13.3 The platform structure (CreatorOS)

**Six AaaS layers:**

| Layer | Function |
|---|---|
| Agent Layer | AI agents as digital workers. Pre-trained, context-rich, task-specific. Can be embedded, licensed, and remixed. |
| Framework Layer | The brains: decision logic, systems thinking, strategy execution frameworks. The source names REIA-001, Clarity Builder, and SkipTrace Flow as examples. |
| Capsule Layer | Self-contained builds (apps, tools, mods, GPTs, prompt stacks, workflows) that users can fork, license, and deploy. |
| Outcome Layer | Users select outcomes instead of features: "Get leads," "Grade cards," "Audit deals," "Generate revenue." |
| Marketplace Layer | Users sell or subscribe to outcomes, powered by agents, wrapped in logic, customizable at will. |
| Rights + Royalties Layer | Creator-first licensing, derivative tracking, monetization of builds, logic, and AI work product. |

**Five CreatorOS layers (top to bottom):**

1. **Creator Identity Layer.** The creator's fully owned, live digital brand. Hero image or embedded video intro, tagline / niche / category badges, custom color theme + layout, agent-hosted welcome message ("Talk to my AI agent"), verified creator tag / license flag.
2. **Live Capsule Feed.** Replaces the post feed. Everything clickable, remixable, monetizable. Each capsule has a remix button, a license tag (free, paid, commercial), a live preview or agent interaction zone, and sell / fork / collab options.
3. **Storefront Layer.** All products, merch, and logic-based goods. Categories: Intelligence Products (agents, GPTs, prompt packs, mini-systems), Media Products (beats, songs, audio templates, AI voice overlays), Game Mods/Tools, Merchandise, Services/Coaching, IP Licenses.
4. **Agent Zone.** Agents trained by the creator, serving the community. Types: Chat Agent (branded voice/logic), Support Agent (guides through products and builds), Builder Agent (helps users remix or deploy a capsule), Booking Agent (schedules services, coaching, DMs).
5. **Remixable Profile Stack.** Every part of the creator experience modular, forkable, customizable: color scheme, layout, capsule feed logic, agent config, embedded integrations (YouTube, Twitch, TikTok, Shopify). Goal: turn every creator into a builder and every fan into a remixing co-creator.

### 13.4 Capsules

A capsule is the fundamental unit: a self-contained, interactive, remixable, monetizable mini-product. A logic object, not a post.

**Capsule types:** prompt packs, buildable templates, music/beat drops, app walkthroughs, mods / mission flows, merch drops, frameworks, livestream clips with agent overlays.

**Every capsule has:** a remix button, a license tag (free, paid, commercial), a live preview or agent interaction zone, and sell / fork / collab options. Capsules carry an outcome promise, remix/fork options, license rights, and download / deploy / buy options. They can be public or paywalled, free to remix or paid to license, auto-expiring or evergreen, and tracked across forks and derivations.

**Live Capsule Feed vs traditional post feed:** the feed is transactional, not consumptive. Every item is clickable, remixable, and monetizable. Content itself is the storefront. The feed prioritizes logic-backed capsules over posts, making it a marketplace of remixable intelligence.

### 13.5 The Creator Identity Layer (White Page 2.0)

Not a Linktree. A living, monetizable identity page backed by AI: a smart identity engine, a remixable storefront, a modular intelligence layer.

**Profile Integration Hub:** creators plug in and showcase every profile: TikTok, YouTube, Twitch, Instagram, Spotify, Soundcloud, Audius, eBay, Etsy, Amazon Store, Facebook Marketplace, Shopify Store, Gumroad, Podia, Kajabi, Discord, Patreon, Substack, personal site, blog, Notion, Calendly, Medium. **Final touches:** License Tracker (what has been licensed, remixed, sublicensed), Remix Analytics (visualize how far ideas travel), Ownership Vault (private archive for IP protection, agent memory, unreleased builds), Collab Zones (invite-only build sessions with revenue sharing), "Powered By" badges (when someone forks or embeds logic, it shows "Built by @username"), AI-Fusion Tools (smart remix suggestions, auto-publishers, growth tactics).

### 14.2 The two levers the old sources missed

**Seeds and reference images are the consistency mechanism now, not text alone.** None of the eight image sources in this document mention seeds. Modern consistency comes from references (--oref / --sref, IP-Adapter, Nano Banana multi-reference) plus seed locking. One roundup reports image references at around 91 percent batch consistency vs 60-70 percent text-only. That figure is one roundup's claim, not independently verified, but the direction is right: lock a reference image and a seed, then swap tokens. Text alone drifts.

**Natural language now outperforms keyword salad on v7/v8.** The old stacks are keyword-dense ("ultra-photoreal 8K master render, golden-hour western sunset, volumetric sun rays..."). On Midjourney v7/v8, a full-sentence description of the same scene performs better. Keep the keyword blocks for SDXL/FLUX/ComfyUI, and write sentence-form versions for Midjourney v7/v8 and Nano Banana.

### 14.3 Per-engine adaptation rules

**Midjourney v7/v8:** use --sref with a style reference image and --sw 0-1000 to control style strength. Use --hd for native 2K on v8. Use Draft Mode for iteration (about 10x faster, half cost), then a full render for the keeper. Use --no for exclusions (Midjourney's only negative mechanism). **Open disagreement, do not pick a winner:** one v7 guide says --cref is DEPRECATED in favor of --oref (Omni Reference, --ow 0-100); other v7 guides still document --cref with --cw 0-100. Test both on your account and record which works.

**Nano Banana / Gemini:** pass reference images (up to 14) for identity and style lock. No negative prompts: phrase exclusions positively or edit after generation. 4K native output. Best for the Remodel Vision Pro flow (Section 10), because the uploaded photo is a reference image natively.

**GPT Image 2 / 2.5:** best instruction-following; give it the full template as sentences. No negative prompts. Best for the Davinci compositing flow (Section 11) where the prompt must be followed literally.

**FLUX 3 Klein:** open weights, runs on 8GB GPU, native 4K, bounding-box layout control (place elements in defined regions, the programmatic version of ControlNet grids). Cheapest per image in the roundups (about $0.009 per 1K). Best for the ComfyUI + ControlNet pipeline.

**Ideogram:** use only when the image must contain text. For everything else, composite text as a layer (Section 11).

**SDXL / ComfyUI:** still the control king via ControlNet. Keep the keyword-dense templates here; they work as written.

### 14.4 What to retire

- Midjourney v6 suffixes (Sections 8, 9): v6 is superseded. v7 is default, v8.2 is current.
- DALL-E 3 / o3 suffixes: superseded by GPT Image 2 / 2.5.
- Gemini 2.5 Image suffixes: superseded by the Nano Banana family.
- SDXL as "the top open option": FLUX 3 Klein is the current open-weight leader.
- Imagen 4: retired August 2026.

## 17. Troubleshooting and fail modes

Merged dials from the Templar stack, the house systems, and the 2026 engine notes. One table, every known failure and its fix.

| Failure | Fix |
|---|---|
| Image looks too clean, too perfect, "AI" | Add wear, patina, chromatic aberration, film grain. Add SSS to foliage and skin. Add atmospherics (dust/mist). |
| Muddy shadows / too dark | Raise fill light (5600K), add rim light, lift the shadow floor in the prompt ("soft fill light, visible shadow detail"). |
| Blown highlights | Add "controlled highlights, preserved sky detail" and drop "volumetric sun rays" to "soft sun glow". |
| Warped geometry (bent rooflines, leaning walls) | Add "mathematically correct perspective" and "straight verticals". On FLUX 3, use bounding-box layout control. |
| Text garbled in the image | Never generate text in the image model. Composite it as an HTML/CSS layer (Section 11). If the image must carry text, use Ideogram. |
| Flags look wrong | Lock the hex codes (Section 8.5). Reduce the flag count in frame. Go macro on one flag at a time. |
| Cross reads as clip-art | Add PBR metal, edge wear, SSS on enamel, Fresnel rim. |
| Cross / shield inconsistent across a series | Lock a reference image and a seed (Section 14.2). Same reference, same seed discipline, same lighting block. |
| Colors drift between shots | Lock the COLOR_PALETTE_TOKEN and the TECH block. Do not re-roll the palette per image. |
| Style drifts between shots | Lock a --sref / --oref reference and --sw / --ow strength. Do not rely on text alone. |
| Midjourney --cref not working | Try --oref / --ow. The guides disagree (Section 14.3); test both and record which works on your account. |
| Negative prompt ignored (GPT Image / Nano Banana) | These engines take no negative prompts. Convert each negative to a positive instruction. |
| Layout collides with text | ControlNet black-and-white grid with reserved negative space (Section 11.5). Generate the background around the text, not under it. |
| Export looks wrong in print | Pillow pass: 300 DPI, CMYK, 0.125 in bleed. Verify at 100 percent before print. Never export print from the generator directly. |
| n8n workflow fails on the code node | Use the corrected builder in Section 4.6. The source's printed code is mangled by a table. |
| Remodel component renders wrong | Fix the Select structure (SelectTrigger / SelectContent wrappers) and actually attach the uploaded image to the generation call. Section 10.2. |
| Series looks like different shoots | Same TECH block, same seed, same reference, same palette on every prompt. Change only the swap token. |
