Retardio: the system, whole

The pieces built on 2026-11-15 already exist separately. This page connects them into one uniform system: one data model, one receipt format, one anchor root, one status dashboard, one convergence table, and one live loop. Nothing here was removed to make it fit. The build is additive, per the standing order: strengthen, do not remove.

What this page is: the convergence build. It wires the Measurement Loop, the Unified System, the On-Chain Anchor v2, the Done/Open Ledger evidence chain, the two Bridges, and the Bridge Builder into a single system with a map, a dashboard, and live controls that do what they say. What it is not: a claim that the system is finished, live in production, or proven. The blocked seams are named on this page, and the numbers that do not exist yet are shown as not existing.

Read this first: what is real, what is not

Real: 25 observations from a public county assessor service; 20 forecasts issued under a frozen rule; a Merkle root recomputed in two languages; 118 ledger items with chained receipts; two allegation maps built from verified sources.

Not real yet: no resolved forecast, no real Brier score, no on-chain anchor, no authority header, no policy gate, no second data source, no promotion. The system is governed, supervised execution with receipts. It is not autonomous, not continuously autonomous, and not in production.

2. One uniform data model

Stated once, used everywhere. Four record schemas, one receipt schema, one canonicalization rule, one anchor root. Anything that does not fit these schemas does not enter the system.

2.2 The canonical receipt schema v1.1

One receipt format for observation, forecast, outcome, gate, promotion, verification, anchor, and build receipts (convergence items 3 and 76). Required fields: receipt_version ("1.1"), receipt_id, receipt_hash, prev_hash, action, actor, timestamp, merkle_root, anchor_root, payload. receipt_id is defined to equal receipt_hash, so it cannot be part of its own hash input. prev_hash is the previous receipt's receipt_hash, or the literal string GENESIS for the first receipt in a chain. merkle_root carries the current manifest root at issuance; anchor_root is null until a real on-chain anchor exists (finish criterion 2 is BLOCKED pending Jeramie's chain/wallet choice). Implemented in verify.js 2.0.0 (browser) and receipts.py (Python); the two must produce identical hashes.

Hashing rule. Canonical JSON: keys sorted bytewise, separators (',', ':'), no whitespace, UTF-8. receipt_hash is the SHA-256 of the canonical JSON of the receipt with receipt_hash and receipt_id removed. All other fields, including prev_hash, are included, so the hash binds the chain.

2.3 The uniform rules

  • One receipt format. Canonical verification receipt v1.1, above. Every chain in this system (loop observations, unified session log, Done Ledger evidence, anchor verification) uses it.
  • One canonicalization rule. Sort keys recursively. Collapse whitespace in strings (trim, collapse internal runs to one space). Lowercase strings. Render whole numbers as integers. UTF-8. No trailing newline.
  • One anchor root. Anchor v2 full root afd56cea3e4abe9265f83c3552cddebac2771ab6d5d50012a641695fd8b8777f (estate root c83c79a84e6fc3c0593516ecf56fc8ebe73156289dfb2cf9ded9f77ce4c1f121), 235 leaves, 0 unverified, 2026-11-15. Every major receipt carries it as merkle_root.
  • One scoring rule. Brier = (1/N) × Σ(pi − oi)², tracked overall, by forecast type, and over time. Published. A model or weight update is retained only if Brier improves on a subsequent or held-out set.
  • One promotion threshold. 200 resolved forecasts before any promotion. Enforced by the gate, not by convention.
  • One human rule. Human approval is mandatory for anything that leaves the system. The system prepares the packet; it cannot send it.

2.4 The two known divergences (honest, pending Jeramie's ruling)

Divergence 1: baseline_v1 is two different rules

The loop's baseline_v1 (2026-11-15): prior 0.04, +0.03 if consideration < $100,000, +0.02 if acreage < 0.5, clamp [0.01, 0.50]. It issued the 20 rapid-flip forecasts (0.04 × 16, 0.07 × 4).

The unified baseline_v1 (2026-11-15): prior 0.15, entity-age / LLC / transfer / consideration terms, clamp [0.01, 0.95]. It refuses on all 25 loop observations (entity_age_days and prior_transfer_count_365d are missing for all 25).

Same name, different rules. Both are implemented and labeled distinctly. The loop's rule is NOT overwritten. Jeramie's ruling on the name is still pending; until then both labels stay.

Divergence 2: canonicalization differs between components

The unified rule lowercases strings. The loop uses strings as returned. The anchor uses no-whitespace canonical JSON with strings as-is. The unified rule is the target for schema_version 1.0. Re-issuing the loop's records under the unified rule would change their hashes, so they are referenced as-is and never re-hashed. Jeramie's ruling on the migration is still pending.

Related deviation, stated on the Done Ledger: only 9 of 118 ledger items cite a content hash (2 SHA-256, 7 MD5). The other 109 record hashes are the SHA-256 of the canonical JSON of the evidence text itself, a hash of the evidence as recorded, not a pre-existing evidence hash.

6. What this system is not

  • No private-individual scoring. Transactions and entity patterns only. No person is scored as "corrupt," "probable corrupt," or ranked by likelihood of wrongdoing. Only LLC names from public records appear in the loop; no private individual is named or scored.
  • No ranking of private individuals as "probable corrupt actors." The typologies stay at the level of published patterns. A pattern match is a forecast about a transaction type, not a finding about a person.
  • No remote surveillance. The only data source is a public county assessor service. Nothing is collected from any person's device, account, or private communication.
  • No charges. No one has been charged as a result of this system. The bridges present allegations as allegations with attribution; a preservation letter is not a charge.
  • No court rulings. No court has ruled on anything in this system. The bridge tallies are 0 of 5 and 0 of 4 on the elements that would have to be proven.
  • No Brier fabricated. The real Brier is NOT YET COMPUTABLE. The only Brier number on this page, 0.0605, is an illustrative worked example on 5 invented rows, labeled as such.
  • No resolution fabricated. 0 resolved forecasts. The resolution windows are closed, but deed history is not in the source, so nothing is coded.
  • No promotion. The gate is closed at 0 of 200 resolved. No rule change has been accepted.
  • No autonomy claimed beyond governed supervised execution with receipts. The system prepares packets; it cannot send them. Human approval is mandatory for anything that leaves the system. The kill switch is a human control.
  • No chain write. The anchor is prepared, not on-chain. The execution path is built; the write awaits Jeramie's chain/wallet choice.
