The Physics of Building AI That Actually Ships

This essay is adapted from "Anatomy Is Dead: The Physics of Building AI That Actually Ships," Book 1 of The Neuruh Papers series. This is the field version.

Your agent worked in the demo. In production it gets slower every turn, the invoice arrives at multiples of the projection, and the team blames the model provider. The provider is usually innocent. The failure is architectural, and you can diagnose it from the token stream alone.

This essay is the discipline: how to budget context, how to respect the cache, how to evaluate systems instead of models, and what actually breaks when real workloads hit.

1. Your context budget is the real bill

Stop treating the context window as a resource to fill. Treat it as expensive real estate. You pay for every token on every turn, and you pay again every time you invalidate the cache. Bigger windows made this worse, not better: a bigger window is a bigger surface for cache invalidation, a bigger bill per turn, and a bigger haystack for the model's attention to get lost in.

The book's rule: information density beats information volume. A 200,000-token window stuffed with undifferentiated retrieved documents is a volume play. A 20,000-token context with dense, structured, relevant, fresh information is a density play. The density play wins on quality, cost, and latency, every time, in every workload the book measured (audit date 2026-09-30).

Long contexts cost you three times: cache memory, per-token compute, and reliability (the documented "lost in the middle" phenomenon). Stuff the window and you pay triple for worse results.

A typical finding from the book's density review of production systems: 30 to 60 percent of context tokens do no work. Retrieved-but-unused documents. Defensive instructions for edge cases that never trigger. Duplicated context from overlapping retrieval. History that should have been compacted. Cut them.

2. The cardinal sin: prefix churn

A transformer generates one token at a time and stores the key and value tensors for everything already processed. That stored state is the KV-cache, and it is the physical constraint everything else follows from. The key mechanic: when two requests share an identical token prefix, the engine reuses the cached tensors for that prefix instead of recomputing them. This is prefix caching, and every major inference provider implements some version of it (audit date 2026-09-30).

The consequence is brutal. In a multi-turn agent loop, everything upstream of the first changed token is cache-eligible, and everything downstream recomputes. Change the beginning of the prompt and you recompute the whole thing.

Prefix churn is any change to early tokens between requests that should share cache. The most common sources, as observed in production (audit date 2026-09-30): a timestamp in the system header (the cache breaks at token ~15 and a multi-thousand-token system prompt recomputes every turn), framework prompt re-rendering, system instructions edited mid-run, nondeterministic tool serialization, retrieved documents prepended above history, and per-tenant identity blocks above shared instructions.

The cost math from the book: a support agent with a 4,000-token system prompt over 30 turns. Cache-aware: roughly 13,000 tokens of input compute. Cache-ignorant with a timestamp header: every turn recomputes from token 1, totaling roughly 255,000 tokens. Same conversation, same model, same outcomes. Roughly 20x the input compute, and latency follows the same curve.

One sentence is the whole rule: no token before the stable prefix may change between requests that should share cache.

3. The three-layer contract

The architecture that falls out of the physics has three layers.

Layer 1, immutable: system identity, role definition, core constraints, output format specifications, tool definitions, few-shot examples. Byte-identical across every request in a deployment, changed only on deployment, versioned like a binary. No timestamps, no per-user data, no dynamic anything. Serialize deterministically.

Layer 2, append-only: conversation history, tool results, observations, persisting retrieved context. Tokens are only ever added to the tail. Nothing is edited, reordered, or deleted during a run. Resist the urge to clean up history in place. Tidiness is the enemy. Append-only is ugly and fast.

Layer 3, dynamic tail: the current user message, the immediate instruction, per-turn retrieved context, timestamps, volatile metadata. Expected to miss cache. That is fine. It is small, and its recomputation cost is bounded.

The contract, stated formally: for any two consecutive requests R1 and R2 in the same run, Layer 1(R1) equals Layer 1(R2) byte for byte, Layer 2(R2) equals Layer 2(R1) plus appended tokens only, and Layer 3 may differ arbitrarily. Satisfy the contract and your cache hit rate is maximized by construction.

Two details that matter. Sizing: put everything genuinely stable in Layer 1, even if it feels long. A 6,000-token immutable layer at 95 percent cache hit rate beats a 2,000-token layer that churns. Stability beats brevity. Compaction: when a long run hits context limits, summarize into a new run's Layer 2 seed at a generation boundary instead of rewriting history in place. Rewriting mid-run is prefix churn wearing a compaction costume.

The "lost in the middle" objection is real: instructions at the top of a long run get less attention. The fix is the Layer 3 reinforcement pattern: restate the currently relevant constraint in the dynamic tail. Just the active constraint for this turn. A small, volatile, cache-expected cost that buys reliability.

4. Separate the brain from the mouth

The second discipline: decouple reasoning from formatting. Let the model reason in free-form thought, then run a separate structured transform that maps that reasoning into a rigid schema. Thinking like a genius and outputting like a machine are two different jobs, and asking one forward pass to do both gets you the worst of both: shallow reasoning and brittle output.

The failure modes are recognizable: truncated reasoning, broken schemas, hedged fields ("confidence": "high-ish"), degrading format compliance over long runs.

The two-pass pattern: pass 1, the brain, reasons freely with no schema constraints beyond "think thoroughly." Pass 2, the mouth, often a smaller or cheaper model, takes the reasoning trace and populates the schema, with constrained decoding enforcing validity. Its job is transformation, not reasoning. The total cost is usually lower than a single coupled pass you have to retry three times because the JSON was invalid.

The book's worked example: a lead-scoring pipeline. Coupled version: one call in eight returned malformed JSON, and scores clustered at 7/10 because the model spent its reasoning budget on format compliance. Decoupled version: schema compliance effectively 100 percent, meaningful score spread, and the reasoning trace available for audit when a score is disputed.

The rule: decouple when the reasoning is the hard part and the format is the brittle part. That is most agentic work.

5. What actually breaks in production

Seven patterns, each observed in real production systems (audit date 2026-09-30; details generalized). If you recognize your system in more than two, stop optimizing the model and start on the audit.

The invoice shock: the pilot measured cost per turn at low turn counts, not cost per completed conversation at production turn counts, where the system rebuilds the full prompt every turn.

The slow death: turn 5 responds in 3 seconds, turn 80 in 45 seconds, and the team blames the provider. Log time-to-first-token against turn number. A steep slope is a cache problem, not a provider problem.

The framework tax: token usage 3x what a hand-rolled version uses, and nobody can explain where the tokens go. The demo was three turns; production runs are 200. If the framework will not let you control token order, it is the wrong tool for production agentic workloads.

The RAG avalanche: retrieval added to "ground" the agent, cost tripled. Retrieved content prepended above history, full-length documents instead of distilled passages, no expiration. Fix: retrieve into the tail, distill to passages, promote to Layer 2 only if the content persists across turns, expire aggressively.

The multi-tenant bleed: per-customer headers above shared instructions, so a 3,000-token shared block recomputes for every request from every tenant. Reorder: shared content first, tenant-specific content in the tail. In real systems this single reordering cut inference spend by more than half.

The schema tax: 10 to 15 percent of calls return malformed output, triggering retries. Coupled reasoning and formatting. Decouple.

The benchmark mirage: the team chose a model from a leaderboard and a smaller, cheaper model with better context architecture beats it on their actual workload. Build the benchmark as your production workload, choose the architecture first, then the cheapest model the architecture makes excellent.

6. Evals as physics

The audit procedure from the book, condensed. Run it quarterly, after every framework upgrade, and before you blame the provider.

Instrument first: the exact token stream per request (not the template, the tokens), cached vs. uncached token counts, latency per turn, turn number, and cost per turn and per run. If your framework does not expose the token stream, that is finding number one.

Then the prefix-stability check: diff ten consecutive turns from a real production run and compute the stable-prefix ratio (tokens before first divergence divided by total tokens). A healthy system diverges only at the tail. Fix Layer 1 violations before optimizing anything else. They dominate everything.

Then the cost curve: plot cost per turn against turn number at the 50th, 90th, and 99th percentile of run length. Flat means cache-coherent. Linearly rising means prefix churn. Superlinear means churn plus volume growth. And compute cost per completed task, not per token. Per-token cost is a provider metric. Per-task cost is a business metric.

Then the density review (sample 50 prompts; what percentage of context tokens were actually referenced; which retrieved documents contributed; what exists for developer comfort rather than model performance) and the decoupling review. Re-evaluate the model only after the architecture is fixed. A cache-ignorant system will mislead you into choosing a bigger model to compensate for architectural waste, which is the most expensive possible response to a fixable problem.

7. Build vs. buy, settled by the physics

The book's commercial shape:

Layer 1, the commodity: models, compute, vector databases, frameworks. Buy it, rent it. Do not build it unless you have a reason measured in millions.

Layer 2, the architecture: your memory design, your retrieval policy, your validation layer, your context lifecycle, your receipt and provenance system. Build this. This is the IP. It is bespoke, hard to copy, and priced on outcomes rather than inputs. The orchestration layer is where the margin lives because it is the only layer that cannot be downloaded.

Layer 3, the outcome: the ranked list, the completed workflow, the decision, the dossier. Sell this. Price it on the outcome, not on the tokens.

This also settles the framework question. Most frameworks in 2025 and 2026 were built by people optimizing for developer experience, not inference physics. Some added caching awareness and deterministic serialization in 2026; others did not. The framework tax is smaller than it was but not gone. Audit the token stream before committing. The cheapest framework on paper can be the most expensive one at 200 turns per run.

8. What 2026 changed

The ledger from the book, honest version. The job title arrived: "context engineering" and adjacent roles became real in 2026, which means cache-aware prompting is table stakes among serious teams, not a secret edge. The edge moved one level up: memory architecture across runs, and evaluation of long-horizon degradation. Provider-side prompt caching went from niche optimization to standard infrastructure across major inference providers (audit date 2026-09-30). The physics did not change. The industry's respect for it caught up.

What the 2025 essay missed, the book corrects: retrieval and multi-tenancy. Retrieval is where half the waste lives, and the essay barely mentioned it. A complete architecture needs a retrieval doctrine: what gets retrieved, in what form, where it lands, when it expires, and how you measure whether it earned its tokens. And cross-tenant cache sharing, via correct token ordering, turned out to be one of the highest-leverage optimizations available.

Multimodality complicated the cache: cached-multimodal-prefix behavior is less mature and less documented than text prefix caching (audit date 2026-09-30). The three-layer architecture still applies, but expect an active engineering frontier through 2027.

And the book keeps its own house clean on the interpretive material: the CEMI consciousness theory, the BDNF-related claims, and the HASI and HKRS formulas appear as labeled framework, not science. The engineering chapters do not depend on any of them.

The build list

Twelve chapters reduce to ten actions. Fix your prompt ordering this week: immutable head, append-only body, dynamic tail, no timestamp header, deterministic serialization. Instrument the token stream. Run the audit quarterly. Decouple your brittle stages. Write your retrieval doctrine. Design for the fleet. Evaluate systems, not models. Build your Layer 2: models commoditize, frameworks converge, your Layer 2 is the thing a competitor cannot download. Price on outcomes. Keep the ledger: date your beliefs, check them later.
